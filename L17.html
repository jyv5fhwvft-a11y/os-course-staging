🎒 EVERYDAY SIMPLIFIED: THE COAT CHECK TICKET

The File Descriptor Metaphor

🎫🧥🔑
The Narrative

When you open a file, the kernel does not hand you the file itself — it hands you a small integer ticket. You present that ticket to read(), write(), and close(). Behind the counter, the kernel has a table mapping ticket #37 → the actual file's internal state. You never touch the file directly.

Execution Path

A file descriptor is an index into a per-process table. It is cheap, portable, and revocable. When you close(), the kernel discards the table entry.

Micro-Accessibility Context

This is the user-space handle through which every file operation flows. The kernel owns the real state; you own only the ticket.

🎒 EVERYDAY SIMPLIFIED: THE BUILDING DIRECTORY

The Root & Absolute Paths Metaphor

🏢📋🔍
The Narrative

A building has one front door — the entrance. From the front door, a directory board lists every department. From each department, another board lists sub-offices. The root directory / is that front door — every absolute path begins there and walks inward. Relative paths, by contrast, are like stepping out of your office and looking at the hallway map from where you stand.

Execution Path

Absolute paths start at the root inode (typically inode #2 on Unix). Relative paths start at the current working directory.

Micro-Accessibility Context

This distinction shapes path resolution — the kernel walks a fixed spine for /path, but must know the working directory context for relative/path.

🎒 EVERYDAY SIMPLIFIED: TWO DOORS TO THE SAME ROOM

The Hard Link Metaphor

🚪🚪🏠
The Narrative

Imagine a room with two doors, both of which enter the same physical space. If you walk in through Door A, you are in the room. If you walk in through Door B, you are in the same room. Neither door is the "real" one — the room itself is what matters.

Execution Path

A hard link is a second name in a directory pointing to the same inode. Both names resolve to the same physical blocks. Deleting one name does not delete the file — only the last reference triggers reclamation.

Micro-Accessibility Context

The inode is the room; directory entries are doors. Multiple doors can lead to the same room.

🎒 EVERYDAY SIMPLIFIED: THE PATH RESOLUTION SUITE

The Summary Metaphor

🔗 Names → Inodes

Names are abstractions over inodes. A directory is a name table mapping strings to inode numbers.

📦 Inodes → Blocks

Inodes are abstractions over blocks. The inode pointer table maps logical file offsets to physical disk blocks.

Each layer hides the one beneath it — and when any layer fails (missing directory, broken soft link, mismatched inode), the whole path fails. Every future lecture — inode layout (L18), journaling (L19) — rests on this foundation.

💻 SYSTEMS COHESION: THE FILE ABSTRACTION LAYER

File Abstractions & File Descriptor Tables

The Two-Level Table Structure

Per-process FD table: int fd → struct file*. Each process owns its own array of 1024 (default) file descriptors.

Global system file table: struct file* → inode*, offset, flags. Shared across all processes that dup() or fork() the descriptor.

The Verdict

Two processes can hold the same underlying open file while sharing the offset — and a third process opening the same path gets a different struct file pointing at the same inode.

All three coexist cleanly.

The key insight: The kernel owns the file state; user space holds only integer tickets into the kernel's per-process table. This separation is the entire security model of file operations.

The struct (ext4 example)

struct ext4_dir_entry_2 {
    __le32 inode;     // inode number
    __le16 rec_len;   // record length
    __u8   name_len;  // name string len
    __u8   file_type; // regular/dir/link
    char   name[];    // null-terminated
};
The Special Entries: Every directory contains . (self) and .. (parent). These are crucial for relative path resolution and cycle detection. Directory lookup is a linear scan of records (or hash-indexed on modern filesystems).
💻 SYSTEMS COHESION: THE VFS PATH WALKER

Path Resolution Walkthrough

1
Start at root. Kernel loads root inode (typically #2 on ext4).
2
Lookup "home." Open root directory file, scan records for home, retrieve inode number (e.g., #45).
3
Lookup "user." Open inode #45's directory file, scan for user, retrieve inode number (e.g., #812).
4
Lookup "resume.pdf." Open inode #812's directory file, scan for resume.pdf, retrieve inode number (e.g., #9042).
5
Return file handle. Load inode #9042 into memory, verify permissions, allocate FD, return ticket.

Every absolute path requires N directory lookups — one per component. Each lookup may require a disk read if the directory block is not cached in memory.

💻 SYSTEMS COHESION: THE UNIVERSAL FILE MODEL

File Types & Mode Bits

The File Type Prefix Letters

- Regular: Ordinary byte-array files (source code, text, binaries).

d Directory: Files whose content is a name→inode table.

l Symbolic Link: Files whose content is a path string.

b Block Device: Disk devices via /dev (from L21).

c Character Device: Byte-stream devices (keyboard, serial).

s Socket: Unix domain socket endpoints.

p Named Pipe (FIFO): Interprocess byte streams.

Why This Matters

This universal file model is the philosophical center of Unix. Device drivers, directories, and pipes are all just files with specialized semantics.

The open() syscall handles them all uniformly. The kernel's VFS layer dispatches based on file type — but the user-space API is identical.

This uniformity is why Unix's "everything is a file" claim is genuinely true.

🔗 SYSTEM PIPELINE: RELIES ON DISK PHYSICS

Core System Cohesion — Relies On L16

Directory Lookup = Disk Read

Every directory lookup is a potential physical disk read. On HDDs, the seek cost dominates — which is why modern file systems cache directory blocks aggressively.

Why Shallow Trees Win

Deep paths mean more lookups mean more possible seeks. This is why classic Unix designs shallow directory trees and why locate (a precomputed index) exists as a fast alternative to walking.

The Architectural Bond

L16 physics shapes L17 abstraction. Every design decision in Unix file systems — from shallow roots to directory caches — is a response to the seek cost of deep path traversal.

Feeds Into L18–L19

L17's path resolution produces an inode number as its final output — the direct input to L18's inode block-pointer walk. And every directory modification (create, rename, delete) requires journaling (L19) to survive power loss.

🔗 SYSTEM PIPELINE: FEEDS INTO INODES AND JOURNALING

Core System Cohesion — Feeds Into L18–L19

L18 (Inodes)

Path resolution ends with an inode number. That inode number is the input to L18's block-pointer walk. The file data itself is stored in blocks pointed at by the inode — never in the directory entry.

L19 (Journaling)

Every directory modification (creating a file, renaming, deleting) requires journaling to survive power loss. The journal must be written before the directory update, ensuring consistency.

The Full Pipeline

User path → L17 resolution → inode number → L18 block walk → physical data. Every step is a cache miss candidate.

The VFS Unity

All these layers are hidden behind the Virtual File System (VFS) interface. open("/path") returns an FD; every subsequent operation routes through the same interface, regardless of filesystem.

🔍 COMPREHENSIVE CRITIQUE: FILE SYSTEM ABSTRACTION

Directory Management Across the Five Paradigms

Monolithic File Systems

The Virtual File System (VFS) layer sits in Ring 0 alongside ext4/XFS/Btrfs. Path resolution, inode caching, and directory reads all happen with full kernel privilege. Fastest, but every filesystem must be vetted for kernel correctness.

Microkernel File Systems

File servers run as user-space processes. VFS becomes an IPC broker between user apps and file servers. FUSE on Linux is a partial realization — file operations call up into user space. Slower, but isolated.

Layered File Systems

Strict VFS → concrete filesystem → device driver stacking. Every operation passes through the same three layers. This is the classic Unix model: open() → VFS → ext4 → block layer.

Modular File Systems

VFS in Ring 0, but concrete filesystems (ext4, XFS, Btrfs, ZFS) load as kernel modules. Filesystems can be added or removed dynamically. FUSE extends this further into user space.

Hybrid File Systems

VFS and hot-path filesystems (ext4, XFS) live in Ring 0; archival, network, or research filesystems run as FUSE daemons. ZFS runs as a kernel module, but remote filesystems (NFS, CIFS) often use user-space drivers.

🏷️ SYSTEM LEXICON: MASTERING THE FILE SYSTEM VOCABULARY

Base File System Terms

Term 01 · File Descriptor

A small non-negative integer returned by the open() system call; acts as a secure session key to access a process's open file lookup array and is passed to read(), write(), and close() to identify the open file. The kernel maintains the actual file state behind the ticket.

(The coat check ticket — you never touch the actual file, only the ticket.)

Term 02 · Directory

A specialized file containing an ordered array ledger of {name, inode_number} record entries, used to map human-readable strings to inode references; includes the special . and .. entries for self and parent resolution. A directory is not a special device — it is a regular file with a specific internal format.

(The nested treasure box whose only content is an index pointing to the next box.)

🏷️ SYSTEM LEXICON: MASTERING THE FILE SYSTEM VOCABULARY

Advanced Link and Path Terms

Term 03 · Inode Number

A filesystem-unique integer identifier that points to a specific inode structure; the actual "address" of a file within a filesystem, distinct from any of its human-readable names. Every directory entry maps a name string to an inode number, and every file operation begins by resolving a path to an inode number.

(The room number behind any door that leads to it.)

Term 04 · Hard Link

A directory entry that points to an existing inode; multiple hard links can reference the same physical file. The inode's i_link_count tracks reference count, and physical blocks are reclaimed only when the count reaches zero and no open file descriptors reference the inode. Cannot span filesystems.

(Two doors that lead to the same room.)

Term 05 · Symbolic Link

A standalone file whose content is a text string representing a path to another file; the symlink has its own inode and metadata, and resolution requires re-walking the path from the beginning. Symlinks may dangle if the target is deleted, and may span filesystems.

(A note on the door saying "I have moved to room 412" — you have to walk to the new room.)

💻 CODE DISSECTION: C PATH RESOLUTION SIMULATOR

Manual Path Resolution Walk

// Demonstrating path component parsing and manual lookup logic
// Compile: gcc -o path path.c && ./path
#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <sys/stat.h>

void trace_path_resolution(const char* full_path) {
    char path_copy[1024];
    strncpy(path_copy, full_path, sizeof(path_copy) - 1);
    path_copy[sizeof(path_copy) - 1] = '\0';

    printf("Resolving path: %s\n", full_path);
    printf("Resolution chain:\n");

    // Walk from root, parsing one component at a time
    char current_path[1024] = "";
    char* component = strtok(path_copy, "/");
    int depth = 1;

    while (component != NULL) {
        strcat(current_path, "/");
        strcat(current_path, component);

        struct stat sb;
        if (stat(current_path, &sb) == 0) {
            printf("  [%d] '%s' -> inode %lu (%s)\n",
                   depth, current_path, (unsigned long)sb.st_ino,
                   S_ISDIR(sb.st_mode) ? "directory" : "file");
        } else {
            printf("  [%d] '%s' -> NOT FOUND (error)\n", depth, current_path);
            return;
        }
        component = strtok(NULL, "/");
        depth++;
    }
    printf("Final target: %s (resolved via %d directory lookups)\n",
           full_path, depth - 1);
}

int main() {
    trace_path_resolution("/home/user/resume.pdf");
    printf("\n");
    trace_path_resolution("/etc/passwd");
    printf("\n");
    trace_path_resolution("/var/log/syslog");
    return 0;
}

Use code with caution.

💻 CODE DISSECTION: TRACING PATH COMPONENT WEIGHTS

Walking the Resolution Trace

strtok(path_copy, "/")

Component split. Splits the path string on / characters. Each call returns the next component. This mirrors the kernel's link_path_walk() in fs/namei.c.

strcat(current_path, component)

The walk prefix. Accumulates the path so far. The kernel maintains the same structure: a struct path holding {vfsmount, dentry} at each step.

stat(current_path, &sb)

The actual lookup. Performs the directory lookup for this component. Kernel equivalents are lookup_fast() and lookup_slow(), both of which consult the dentry cache before touching disk.

sb.st_ino

The inode number. For intermediate components, this is a directory inode; for the final component, it is the target file's inode.

The Chain Cost

/home/user/resume.pdf requires 3 directory lookups. /etc/passwd requires only 2. Path depth is path cost.

The Kernel's Real Walker

The real link_path_walk() handles symlinks (trailing_symlink()), permissions (may_lookup()), and mount points (follow_down()). Same fundamental algorithm.

🏆 RETROSPECTIVE: SYLLABUS DISSECTION SUMMARY

Grand Lecture Summary

01

A directory is not a special device — it is a regular file containing a table of {name, inode} records. Every path lookup walks that table component by component from the root inode. Path depth directly determines lookup cost, which is why shallow trees and directory caching matter on HDDs.

02

The kernel hands user space file descriptors — small integer tickets — while it maintains the real file state in a two-level FD → struct file → inode table behind the scenes. User space never touches the actual file; it only presents tickets.

03

Hard links are additional directory entries pointing to the same inode (shared content). Soft links are separate files whose content is a target path string (indirect redirection). The inode's reference count controls when actual blocks are reclaimed — only when the last hard link is removed and no open FDs remain.
