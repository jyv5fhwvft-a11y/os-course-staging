🎒 EVERYDAY SIMPLIFIED: THE LIMITED DESK & THE LIBRARY STACKS

The Demand Paging Metaphor

📚🪑📖
The Narrative

You are studying in a massive university library. Your study desk fits only 3 books at a time. You are writing an essay referencing 10 different books. You start working; you look for Book A on your desk. It's not there! — you must pause, wait for a runner to fetch Book A from the deep basement stacks, and drop it onto your desk. When your desk fills up and you need a 4th book, you must choose which book to throw off and send back to the basement.

Execution Path

Desk = physical RAM frames. Basement stacks = disk swap space. Missing book = page fault. Book eviction = page replacement policy.

Micro-Accessibility Context

Every page fault costs a disk round-trip — enormously expensive. The entire art of demand paging is minimizing faults.

🎒 EVERYDAY SIMPLIFIED: THE STREAMING VIDEO BUFFER

The Demand Loading Metaphor

🎬📥💾
The Narrative

Streaming video platforms do not download the entire 4K movie file before playing. They load only the immediate 10 seconds of content into local memory, then discard old data as playback advances. When you scrub to a new section, the player fetches just that section. The video file is 20 GB — but only a few megabytes are ever actively in memory.

Execution Path

The virtual address space is the full 20 GB "movie." Physical RAM holds only the currently-playing "buffer." Missing sections are loaded on demand — the exact model of demand paging.

Micro-Accessibility Context

Demand paging lets applications be larger than physical RAM — as long as accesses exhibit locality, most pages are never loaded at all.

🎒 EVERYDAY SIMPLIFIED: THE CLOSET FULL OF CLOTHES

The Replacement Metaphor

👕👖🧳
The Narrative

Your closet holds 10 outfits. Winter brings new clothes, but you cannot expand the closet. To make room for a new coat, you must evict an existing outfit — which one do you choose? FIFO: evict the oldest outfit, regardless of whether you wear it. LRU: evict the outfit you have not worn in the longest time. Optimal: evict the outfit you will need farthest in the future.

Execution Path

The replacement policy decides which page to evict when a fault occurs and RAM is full. Policy quality directly determines fault rate and application performance.

Micro-Accessibility Context

Every eviction is a potential future fault. The better the policy predicts the future, the lower the fault rate.

🎒 EVERYDAY SIMPLIFIED: THE THRASHING COLLAPSE

The Thrashing Metaphor

🔄💥🐌
The Narrative

Your closet is 10 outfits — but you own 100 coats and need all 100 every morning. Every new coat evicts another coat you need immediately. You spend the entire day running clothes in and out of storage, never actually wearing anything. The system is completely saturated — a thousand closet operations per hour, zero actual productivity.

Execution Path

Thrashing is the pathological state where the OS spends more time swapping pages in and out than executing actual user code. Caused by too many processes competing for too few frames.

Micro-Accessibility Context

Thrashing is a catastrophically unrecoverable state — once triggered, the system appears frozen. The only fix is to reduce the number of competing processes.

🎒 EVERYDAY SIMPLIFIED: THE VIRTUAL MEMORY SUITE

The Summary Metaphor

✅ What Demand Paging Provides

Programs larger than physical RAM. Instant process startup (load only the working set). Efficient memory sharing (read-only code pages shared across processes). Fast process creation (copy-on-write, from L06).

❌ What It Costs

Page fault overhead (~10–100 microseconds per disk access — millions of cycles). Thrashing if frame allocation is wrong. Complexity of the replacement policy. Disk I/O bandwidth is scarce.

Demand paging is the single most transformative memory mechanism of the past 60 years. It is why modern systems can run hundreds of processes on a machine with a few GB of RAM.

💻 SYSTEMS COHESION: THE LAZY LOADING MECHANISM

Demand Paging Fundamentals

The Core Idea

Instead of loading all of a process's pages into RAM at startup, the OS loads only the pages that are actually accessed — and only when they are accessed.

Present/Absent Bit: Each page table entry has a valid bit. Valid=1 means the page is in RAM. Valid=0 means the page is not in RAM — it must be loaded from disk (or swap) on first access.

Lazy Loading: A process starts with almost no pages in RAM. Pages are loaded one at a time, on demand.

The Economics

Startup cost: Instead of loading an entire 500 MB application, load only the 50 MB hot working set. Process startup is 10× faster.

Idle cost: An unused feature in an application never loads its pages. Memory not needed is not consumed.

Sharing: Read-only code pages (libc.so, browser rendering engine) can be shared between processes. Load once, use everywhere.

💻 SYSTEMS COHESION: THE PAGE FAULT EXCEPTION

What Triggers a Page Fault

1

CPU accesses virtual address. The MMU looks up the page table entry — but valid = 0 (page not present in RAM).

2

MMU raises page fault trap. The CPU suspends the current instruction, saves the faulting address in CR2, and switches to Ring 0 (L02's trap mechanism).

3

Kernel page fault handler runs. The kernel verifies the fault is legitimate (the page is valid but not yet loaded) vs. illegitimate (the address is not mapped at all → SIGSEGV, from L24's memory protections).

4

Load page from disk. A free frame is allocated. The page is read from disk (swap or file) into the frame. The page table is updated (valid = 1, frame number written).

5

Retry the instruction. The faulting instruction is re-executed. This time the translation succeeds and the memory access completes normally.

Cost: A page fault takes 10–100 microseconds (disk I/O dominated) — millions of CPU cycles, hundreds of times slower than a memory access. Every fault is expensive, which is why the replacement policy matters so much.
💻 SYSTEMS COHESION: THE FIFO REPLACEMENT POLICY

First-In-First-Out (FIFO) Page Replacement

The Policy

Maintain a simple FIFO queue of loaded pages. On a fault, evict the oldest page — the one that was loaded the longest time ago.

Implementation: A circular queue of frame references. Very cheap to implement — no access tracking needed.

Weakness: Evicts the oldest, regardless of whether it is heavily used. A hot page loaded long ago can be evicted even though it will be needed immediately.

Belady's Anomaly

FIFO can exhibit Belady's Anomaly — an increase in the number of frames can cause an increase in the number of page faults. This is mathematically counterintuitive (more RAM should mean fewer faults) but is a real property of FIFO.

Belady's Anomaly does NOT occur with LRU or Optimal — those are "stack algorithms" and always improve monotonically with more frames.

💻 SYSTEMS COHESION: THE LRU REPLACEMENT POLICY

Least Recently Used (LRU) Page Replacement

The Policy

Maintain an access-order tracking of pages. On a fault, evict the page that has not been accessed for the longest time.

Implementation: Requires tracking access order — typically via a doubly-linked list (O(1) move-to-front on access) or a counter with a min-heap (O(log n) per access).

Strength: Excellent approximation of optimal behavior. Based on the locality principle — recently used pages are likely to be used again.

Why LRU Works

Programs exhibit temporal locality — recently accessed pages are likely to be accessed again soon. LRU is the natural replacement policy for this workload characteristic.

No Belady's Anomaly: LRU is a stack algorithm — the set of pages in n frames is always a subset of pages in n+1 frames. More frames always reduces faults.

LRU is the gold standard — but tracking access times exactly is expensive. Real systems approximate it.

🔗 SYSTEM PIPELINE: RELIES ON PAGING & TLB

Core System Cohesion — Relies On L11 & L12

L11 (Paging)

Demand paging is just paging with the valid bit meaningfully used. The page table structure, MMU translation, and page fault exception mechanism all come directly from L11.

L12 (TLB)

When a page is evicted, its TLB entry becomes stale — the TLB must be invalidated. On multi-core systems, the kernel must send TLB shootdowns (from L12's ASID discussion) to flush the entry from every core's TLB.

The Architectural Bond

Demand paging + TLB + swap together form virtual memory. Every layer relies on the one below: demand paging uses page tables, page tables are cached in TLB, TLB misses trigger page table walks, page table walks may trigger page faults.

Feeds Into L14–L15 (Sync)

Concurrent accesses to the page fault handler require careful synchronization — this is why Module 4 (L14–L15) directly follows Module 3.

🔗 SYSTEM PIPELINE: FEEDS INTO L16–L19 FILESYSTEM

Core System Cohesion — Feeds Into Module 5

Swap Space

Demand paging requires a place to store evicted pages — typically a dedicated disk partition or swap file. L16–L19's disk geometry, inode layout, and journaling directly determine swap performance.

Memory-Mapped Files

L17's file abstraction can be unified with paging: a file's contents can be mapped directly into the process address space via mmap(). Reads and writes to the mapped pages become file reads and writes transparently — the page cache is the file cache.

Page Cache

The kernel caches file blocks in RAM pages. When a file is read multiple times, the second read may hit the page cache — no disk access needed. The page cache is the primary reason Linux file I/O feels fast even on slow disks.

The Unity

In modern Linux, "file pages," "anonymous pages," and "shared pages" all coexist in one unified page cache with one unified eviction policy. This is the fundamental architecture that makes Linux memory management efficient.

🔍 COMPREHENSIVE CRITIQUE: DEMAND PAGING STRATEGIES

Page Replacement Across the Five Paradigms

Monolithic Paging

Page replacement policy (LRU approximation, CFS-based) managed entirely in Ring 0. The kernel maintains page reference counters (per-page access timestamps), scans them periodically (clock algorithm), and decides evictions inline with page faults. Fast but inflexible.

Microkernel Paging

Page replacement policies can be delegated to user-space pager services. The kernel handles only the fault itself; a user-space server decides which page to evict. Slower (extra IPC) but policies can be swapped at runtime — even mid-execution.

Layered Paging

Strict layering: page fault handler → page replacement policy → disk I/O pipeline. Each layer is independently verifiable and testable. Policy changes require only the middle layer to be swapped.

Modular Paging

Multiple replacement algorithms (LRU, clock, ARC, active/inactive lists) shipped as swappable modules. Linux 2.6+ has modular page replacement policies (kswapd manages different list types).

Hybrid Paging

Modern Linux uses a two-list hybrid — an "active" list (recently accessed, protected from eviction) and an "inactive" list (candidates for eviction). Pages are promoted to active on second access, demoted on aging. This approximates LRU at much lower cost than exact tracking.

🏷️ SYSTEM LEXICON: MASTERING THE VIRTUAL MEMORY VOCABULARY

Base Virtual Memory Terms

Term 01 · Demand Paging

An optimization mechanism where virtual pages are loaded into physical RAM strictly on-demand — only when an active instruction actually requests them. Contrasted with eager loading (load all pages at process start). The primary enabler of programs larger than physical RAM.

(The library patron who only fetches books from the basement when actually needed.)

Term 02 · Page Fault

A valid hardware exception interrupt triggered when a thread attempts an operation on a page marked as absent from physical RAM (valid bit = 0). The kernel's page fault handler either loads the page from disk (legitimate fault) or terminates the process (illegal access — SIGSEGV).

(The discovery that the book you wanted is not on your desk — it must be fetched from the stacks.)

🏷️ SYSTEM LEXICON: MASTERING THE VIRTUAL MEMORY VOCABULARY

Advanced Virtual Memory Terms

Term 03 · Swap Space

A designated raw block sector layout on a hard drive or SSD used to cache evicted virtual page overflows. When RAM is full and a page is evicted, it is written to swap. When it is accessed again, it is swapped back in from disk — costing tens of microseconds per swap operation.

(The deep basement storage where evicted books wait to be requested again.)

Term 04 · Thrashing

A critical system failure state where the machine spends more time continuously swapping pages back and forth to disk than executing actual instruction paths. Caused by over-committing memory — running more processes than the working-set size can support. The only fix is to reduce process count (kill or pause processes).

(The librarian who spends the entire day running books to and from the basement, never letting anyone actually read.)

Term 05 · Belady's Anomaly

A pathological property of the FIFO page replacement policy where increasing the number of available frames can increase the number of page faults. Mathematically counterintuitive (more RAM should mean fewer faults) but a real property of non-stack algorithms. LRU and Optimal do not exhibit this anomaly.

(Adding a bigger closet somehow makes you do more laundry — only happens with FIFO's particular flaw.)

💻 CODE DISSECTION: C PAGE REPLACEMENT SIMULATOR

Simulating FIFO and LRU Page Replacement

// Simulating FIFO and LRU page replacement in C
// Compile: gcc -o paging paging.c && ./paging
#include <stdio.h>
#include <stdbool.h>

#define MAX_FRAMES   4
#define MAX_REFS     20

// ---------- FIFO Page Replacement ----------
int fifo_replace(int refs[], int n, int n_frames) {
    int frames[MAX_FRAMES];
    int next_slot = 0;       // Points to the next frame to evict
    int faults = 0;

    for (int i = 0; i < n_frames; i++) frames[i] = -1;  // Empty

    printf("\n=== FIFO (frames=%d) ===\n", n_frames);
    printf("Ref  Frames           Fault?\n");

    for (int i = 0; i < n; i++) {
        int page = refs[i];
        bool hit = false;

        // Check if page is already in a frame
        for (int f = 0; f < n_frames; f++) {
            if (frames[f] == page) { hit = true; break; }
        }

        if (!hit) {
            // Evict via FIFO: replace the oldest-loaded frame
            frames[next_slot] = page;
            next_slot = (next_slot + 1) % n_frames;
            faults++;
        }

        printf("%2d   ", page);
        for (int f = 0; f < n_frames; f++) {
            if (frames[f] == -1) printf(" -  ");
            else printf("%2d  ", frames[f]);
        }
        printf("  %s\n", hit ? "HIT" : "FAULT");
    }
    printf("Total FIFO faults: %d\n", faults);
    return faults;
}

// ---------- LRU Page Replacement ----------
int lru_replace(int refs[], int n, int n_frames) {
    int frames[MAX_FRAMES];
    int last_used[MAX_FRAMES];   // Timestamp per frame
    int faults = 0;
    int time_counter = 0;

    for (int i = 0; i < n_frames; i++) {
        frames[i] = -1;
        last_used[i] = -1;
    }

    printf("\n=== LRU (frames=%d) ===\n", n_frames);
    printf("Ref  Frames           Fault?\n");

    for (int i = 0; i < n; i++) {
        int page = refs[i];
        bool hit = false;
        time_counter++;

        // Check if page is in a frame
        for (int f = 0; f < n_frames; f++) {
            if (frames[f] == page) {
                hit = true;
                last_used[f] = time_counter;  // Update access time
                break;
            }
        }

        if (!hit) {
            // Find the least-recently-used frame
            int lru_slot = 0;
            for (int f = 1; f < n_frames; f++) {
                if (last_used[f] < last_used[lru_slot]) lru_slot = f;
            }
            frames[lru_slot] = page;
            last_used[lru_slot] = time_counter;
            faults++;
        }

        printf("%2d   ", page);
        for (int f = 0; f < n_frames; f++) {
            if (frames[f] == -1) printf(" -  ");
            else printf("%2d  ", frames[f]);
        }
        printf("  %s\n", hit ? "HIT" : "FAULT");
    }
    printf("Total LRU faults: %d\n", faults);
    return faults;
}

int main() {
    // Classic reference string from OS textbooks
    int refs[MAX_REFS] = {7, 0, 1, 2, 0, 3, 0, 4, 2, 3, 0, 3, 2, 1, 2, 0, 1, 7, 0, 1};
    int n = 20;

    printf("Reference string: ");
    for (int i = 0; i < n; i++) printf("%d ", refs[i]);
    printf("\n");

    int fifo_faults_3 = fifo_replace(refs, n, 3);
    int lru_faults_3  = lru_replace(refs, n, 3);

    printf("\n=== Comparison ===\n");
    printf("FIFO: %d faults | LRU: %d faults\n", fifo_faults_3, lru_faults_3);
    printf("Winner: %s\n",
           lru_faults_3 < fifo_faults_3 ? "LRU" :
           fifo_faults_3 < lru_faults_3 ? "FIFO" : "TIE");

    return 0;
}

Use code with caution.

💻 CODE DISSECTION: TRACING THE REPLACEMENT ARITHMETIC

Walking the Page Replacement Trace

FIFO: next_slot pointer

The FIFO queue. The next_slot variable points to the oldest frame. On each fault, the new page goes into next_slot, and next_slot advances circularly. No access tracking — just a rotating pointer.

FIFO behavior on the trace

Trace result: FIFO produces 15 faults on the 20-reference string with 3 frames. It evicts pages based purely on load order, ignoring whether they are hot.

LRU: last_used timestamps

The LRU queue. Each frame has a last_used timestamp. On a hit, the timestamp is updated. On a fault, the frame with the smallest timestamp (least recently used) is chosen as the victim.

LRU behavior on the trace

Trace result: LRU produces 12 faults on the same trace with 3 frames — 3 fewer faults than FIFO. LRU performs better because it captures the temporal locality of the reference pattern.

Why LRU wins on realistic traces

The trace has clear locality — recent pages (0, 3, 2, 1) are re-referenced repeatedly. LRU keeps them in memory. FIFO evicts some of them because they were loaded early, causing unnecessary faults.

The Real-World Reality

Exact LRU is expensive (requires updating timestamps on every access). Linux uses an approximation via the clock algorithm with two lists (active/inactive) — nearly as good as LRU, far cheaper.

🎯 INTERACTIVE WORKSHOP: THE HUMAN REFERENCE STRING LRU SIMULATION

The Physical LRU Simulation Game

The Setup

Line up 3 empty chairs at the front of the room — these are the 3 RAM frames. One student acts as the "replacer" holding a stopwatch.

The Players

Students 1–5 each hold a card with a number (representing a page). The instructor calls out a sequence of page numbers.

The Rules

When the instructor calls a page:

· If the page's student is already seated, that student is "hit" — move them to the newest chair to mark recency.

· If not, the student rushes to an empty chair.

· If no chair is empty, the "least recently used" student must leave their chair, and the new student sits.

The Discovery: The class counts the number of evictions (faults). Then repeat the same sequence with the FIFO rule — the oldest occupant leaves when the chairs fill. Compare the fault counts. On the classic reference string 7, 0, 1, 2, 0, 3, 0, 4, 2, 3, 0, 3, 2, 1, 2, 0, 1, 7, 0, 1, LRU produces 12 faults while FIFO produces 15 — a real 20% reduction.

🏆 RETROSPECTIVE: SYLLABUS DISSECTION SUMMARY

Grand Lecture Summary

01

Demand paging loads virtual pages into RAM only when accessed, using the page table's valid bit to track which pages are present. It enables programs larger than physical RAM, faster process startup, and page sharing between processes — the single most transformative memory mechanism of the past 60 years.

02

Page replacement policies decide which page to evict when RAM is full. FIFO is simple but evicts hot pages and can exhibit Belady's Anomaly (more frames → more faults). LRU evicts the least-recently-used page, matching temporal locality, and never exhibits Belady's Anomaly — but exact LRU is expensive, so real systems use approximations (clock algorithm, active/inactive lists).

03

Thrashing is the catastrophic failure state where the OS spends more time swapping pages than executing code. Caused by over-committing memory — too many processes competing for too few frames. The only fix is to reduce process count. Modern Linux's active/inactive list hybrid, plus sophisticated memory cgroup accounting, makes thrashing rare — but it still happens under extreme memory pressure.
