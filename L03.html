The Core Objective

Trace a system call pathway from its user-space declaration down through hardware trap handling and kernel interrupt vector lookup.

The Problem Hook: L02 established the wall — the hardware barrier between user code and kernel code. But if the wall is absolute, how does any legitimate operation ever happen? A user program needs to open files, spawn processes, allocate memory, and send network packets — all of which require kernel privilege. The wall must have a gate — but only one gate, with a strict protocol for who may pass through, what they may request, and how the kernel validates every request.

🎒 EVERYDAY SIMPLIFIED: THE BANK TELLER COUNTER

The Syscall Metaphor

🏦🪟💵
The Narrative

You want to withdraw money from your savings account. Because of security protocols, you cannot simply walk past the guards and open the steel vault yourself. Instead, you must approach a secure bulletproof teller window. You write your specific request on an explicit withdrawal form (the syscall number) and pass it through a slot. The teller (the kernel handler) reads your slip, verifies your ID, opens the vault safely on your behalf, and passes back your cash.

Execution Path

The teller window is the syscall boundary. You can only request operations — you cannot perform them yourself.

Micro-Accessibility Context

The controlled request-submit-receive protocol across the security boundary.

🎒 EVERYDAY SIMPLIFIED: THE HASH MAP ROUTER

The Dispatch Metaphor

📋🔢🔀
The Narrative

A switchboard operator at a giant index board with rows numbered 0–450, each paired with a function name — read, write, open, fork, exit. The index key is a positive numeric ID (e.g., syscall #1 for write, #57 for fork). The value paired with that key is a strict pointer to a verified, compiled inner kernel function array location.

Execution Path

The syscall number loaded into rax is used as an index into the sys_call_table. O(1) dispatch, easy to validate (out-of-range numbers rejected).

Micro-Accessibility Context

The internal dispatch structure — the hash-map-style lookup that routes requests to handlers.

🎒 EVERYDAY SIMPLIFIED: THE FORM FIELDS

The Register Marshalling Metaphor

📝⚙️📤
The Narrative

Every bank form has standardized fields — the teller knows exactly where to look for the account number, the amount, the signature. The syscall interface has standardized register fields — rax always holds the syscall number, rdi the first argument, rsi the second. The kernel does not need to guess.

Execution Path

Argument passing is a convention enforced by libc, the syscall stub, and the kernel's ABI. Breaking the convention is rejected.

Micro-Accessibility Context

The input marshalling mechanism — arguments cross the barrier through standardized register fields.

🎒 EVERYDAY SIMPLIFIED: THE EMERGENCY NUMBERS BOARD

The Vector Table Metaphor

📞📋🚨
The Narrative

When you dial an emergency number, you do not call the fire department directly — you call the emergency dispatch center, which looks up your number against the directory and routes to the correct service. This is the Interrupt Vector Table (IVT). The CPU does not call the syscall handler directly — it calls the dispatcher, which consults a table to find the right handler.

Execution Path

The IVT is a fixed-location array in memory, established by the kernel at boot. Each entry holds a code pointer to the corresponding handler.

Micro-Accessibility Context

The routing layer — the CPU vector table that directs control to the syscall dispatcher.

🎒 EVERYDAY SIMPLIFIED: THE GATEKEEPER SUITE

The Summary Metaphor

📤 User Side

Submit a request through standardized register fields — rax (number), rdi, rsi, rdx (arguments). Then execute the syscall instruction.

📥 Kernel Side

Trap, dispatch, validate arguments, execute the operation, return the result via rax.

The syscall interface is a protocol, not a single function. Each stage is strictly enforced — the protocol does not tolerate improvisation.

💻 SYSTEMS COHESION: THE INDEX KEY

The Syscall Number Convention

Fixed per Architecture

On x86-64, read is always 0, write is always 1, open is always 2, close is always 3. Changing them would break every compiled program ever shipped.

Where they live: /usr/include/asm/unistd_64.h — one of the most stable files in Linux.

Range: x86-64 has syscalls 0–~340 assigned. ARM64 has its own numbers.

Common Syscall Numbers (x86-64)

read(0) · write(1) · open(2) · close(3)

stat(4) · fstat(5) · lseek(8)

mmap(9) · mprotect(10) · munmap(11) · brk(12)

ioctl(16)

fork(57) · execve(59) · exit(60)

wait4(61) · kill(62)

The Verdict: Every program operation that requires kernel privilege starts with a numeric syscall number in a register. The number is not a secret — it is a protocol constant.
💻 SYSTEMS COHESION: THE ABI INPUT SCHEMA

The Register Argument Convention

rax

Syscall number (input). Also the return value (output).

rdi

Argument 1 — e.g., file descriptor for read.

rsi

Argument 2 — e.g., buffer pointer.

rdx

Argument 3 — e.g., byte count.

r10

Argument 4. (Not rcx — rcx is clobbered by syscall.)

r8 & r9

Arguments 5 and 6.

Return value: Always in rax. Negative values indicate errors (-errno, e.g., -ENOENT = -2). Positive or zero indicates success.
💻 SYSTEMS COHESION: THE HARDWARE TRANSITION

The Syscall Trap Sequence

User → Kernel

1. Arguments in place (rax, rdi, rsi, …)

2. Execute the syscall instruction (0F 05)

3. CPU saves RIP to rcx, RFLAGS to r11

4. CPL switches from 3 to 0

5. Loads new segments from MSR_STAR

6. Jumps to handler at MSR_LSTAR

7. Kernel entry stub saves registers → pt_regs

Kernel → User (Return)

1. Handler completes, return value in pt_regs.ax

2. Kernel executes sysret (or sysretq)

3. CPU restores RIP from rcx, RFLAGS from r11

4. CPL switches from 0 to 3

5. Jumps back to user code after syscall

Cost: The entire trap sequence takes ~100 ns to ~1 μs — fast enough for thousands of syscalls per second per process, but slow enough that batching matters.
💻 SYSTEMS COHESION: THE HANDLER LOOKUP

The Syscall Dispatch Table

The Table Structure

What it is: A C array of function pointers, defined in arch/x86/entry/syscall_64.c.

The dispatcher: do_syscall_64() reads regs->ax, validates against NR_syscalls, calls sys_call_table[nr].

Handler's job: Extract args from pt_regs, validate user pointers, call actual kernel implementation, write result back to rax.

The Security Concern

The sys_call_table is in read-only kernel memory after boot (CONFIG_STRICT_KERNEL_RWX=y).

An exploit that overwrites a table entry would gain arbitrary kernel code execution — a classic attack. This is why the table is protected.

Verdict: O(1) lookup. Its correctness is critical — a missing or corrupted entry breaks every program that depends on that syscall.

💻 SYSTEMS COHESION: THE TRUST BOUNDARY

The Critical Security Boundary — Pointer Validation

The Pointer Validation Problem

User code passes a pointer (e.g., buffer to read()).

The kernel cannot simply dereference it — the address might be:

· Unmapped (not in the user's page tables)

· Read-only (but the syscall expects a write pointer)

· Pointing to kernel memory (maliciously-crafted)

· Maliciously aligned to break hardware assumptions

The Kernel's Approach

copy_from_user / copy_to_user: Specialized functions that check the user pointer against the process's memory map, then copy safely. On fault, return -EFAULT.

access_ok(): Cheap initial check that address is in user space — necessary but not sufficient.

get_user / put_user: For single primitive types.

Never memcpy directly from user pointers — the classic security bug that has caused the most severe kernel CVEs.

🔍 COMPREHENSIVE CRITIQUE: KERNEL SYSCALL STRATEGIES

Syscall Strategies Across the Five Paradigms

Monolithic Syscall Handling

Single system call table with hundreds of entries, each pointing deep in the monolithic kernel. Direct, fast, O(1). Every syscall runs at full Ring 0 privilege. Weakness: a bug in any handler is kernel-wide compromise.

Microkernel Syscall Handling

Much smaller system call table (< 100 syscalls). Handlers often just translate requests into IPC messages and forward to user-space servers. Syscalls become IPC operations — slower, but bugs cannot crash the kernel.

Layered Syscall Handling

Strict dispatch pipeline: generic ABI layer → subsystem dispatch → specific handler. Each layer adds overhead but improves modularity. Errors caught at layer boundaries.

Modular Syscall Handling

The system call table is fixed, but handlers are thin wrappers that dispatch to loadable modules. ioctl() is the extreme case — dispatches by device-specific codes.

Hybrid Syscall Handling

Core syscall table handles critical operations in-kernel; optional syscalls (io_uring, eBPF, sched_ext) dispatch to specialized subsystems with their own validation. Modern Linux is functionally hybrid.

🏷️ SYSTEM LEXICON: MASTERING THE SYSCALL VOCABULARY

Base Syscall Terms

Term 01 · System Call (Syscall)

The programmatic interface used by user-space applications to request core kernel services; a controlled transition from Ring 3 to Ring 0 triggered by the syscall assembly instruction, which the kernel handles via a fixed dispatch table and then returns the result to user space. It is the only legitimate way for user code to access kernel privileges.

(The bank teller window — the only authorized route to the vault.)

Term 02 · Hardware Trap

An exceptional condition generated by software (e.g., the syscall instruction) or hardware that shifts control back to the operating system's supervisor code; distinct from hardware interrupts (asynchronous external events) in that traps are synchronous with the instruction stream.

(The electronic signal that summons the manager when the teller requests vault access.)

🏷️ SYSTEM LEXICON: MASTERING THE SYSCALL VOCABULARY

Advanced Syscall Terms

Term 03 · Interrupt Vector Table

A memory array holding code pointers to specialized driver and kernel function routines. On modern x86-64, it is called the Interrupt Descriptor Table (IDT). Set up by the kernel at boot; stored in protected memory.

(The emergency numbers board — the CPU dials the appropriate number for each event.)

Term 04 · Syscall Register Number

The specific integer key loaded into rax to tell the OS which system service to route to. It is a fixed protocol constant — the same number identifies the same syscall across all programs on the same architecture.

(The specific form number you must fill out at the teller window.)

Term 05 · copy_from_user / copy_to_user

Specialized kernel functions that safely copy data between kernel and user buffers; they validate the user pointer against the process's address space and handle page faults without crashing the kernel. Direct memcpy from user pointers is a critical vulnerability.

(The teller's careful ID verification before touching the vault.)

💻 CODE DISSECTION: C RAW SYSCALL PANEL

Bypassing libc to Invoke the Raw Syscall

// Bypassing the libc wrapper and invoking a raw x86_64 write syscall
// COMPILE: gcc -o rawsyscall rawsyscall.c
#include <stdio.h>
#include <unistd.h>
#include <string.h>

int main() {
    const char* msg = "Hello from a raw x86_64 system call!\n";
    size_t msg_len = strlen(msg);

    printf("[USER MODE] Invoking raw syscall 'write' (number 1)...\n");
    printf("[USER MODE] Arguments via rdi/rsi/rdx, number via rax.\n\n");
    fflush(stdout);

    // Linux x86-64 syscall number for 'write' is 1.
    // Syscall ABI: rax=number, rdi=arg1, rsi=arg2, rdx=arg3
    //   rax = 1     (SYS_write)
    //   rdi = 1     (file descriptor 1 = stdout)
    //   rsi = msg   (pointer to buffer)
    //   rdx = 37    (byte count)
    // The 'syscall' instruction traps from Ring 3 to Ring 0.

    long result;
    __asm__ volatile (
        "movq $1, %%rax\n\t"       // Syscall number 1 = 'write'
        "movq $1, %%rdi\n\t"       // Arg 1: FD 1 (stdout)
        "movq %1, %%rsi\n\t"       // Arg 2: pointer to message
        "movq %2, %%rdx\n\t"       // Arg 3: message length
        "syscall\n\t"              // Invoke kernel — trap to Ring 0
        "movq %%rax, %0\n\t"       // Save return value from rax
        : "=r"(result)
        : "r"(msg), "r"(msg_len)
        : "%rax", "%rdi", "%rsi", "%rdx", "memory"
    );

    printf("\n[USER MODE] Returned from kernel.\n");
    printf("[USER MODE] Syscall returned: %ld bytes written\n", result);

    if (result < 0) {
        printf("[USER MODE] Syscall failed with error %ld\n", -result);
    } else {
        printf("[USER MODE] Success! Kernel wrote %ld bytes for us.\n", result);
    }
    return 0;
}

Use code with caution.

💻 CODE DISSECTION: TRACING THE SYSCALL PIPELINE

Walking the Raw Syscall Trace

movq $1, %%rax

Set the syscall number. rax = 1 — the fixed number for write. The dispatch key the kernel will read.

movq $1, %%rdi

Arg 1 = file descriptor. rdi = 1 — stdout. Every process starts with fds 0, 1, 2 open.

movq %1, %%rsi

Arg 2 = buffer pointer. The address of our message string. This is a user-space pointer — validated by the kernel.

movq %2, %%rdx

Arg 3 = length. The kernel will copy exactly this many bytes.

syscall

The trap. Saves RIP to rcx, RFLAGS to r11, switches CPL 3→0, jumps to handler at MSR_LSTAR. Kernel entry stub saves registers to pt_regs.

Dispatch & Execute

do_syscall_64() reads regs->ax = 1, looks up sys_call_table[1] = __x64_sys_write. Handler validates rsi, calls vfs_write, copies bytes with copy_from_user, returns 37.

movq %%rax, %0

Read rax back into local result. Value from the kernel via the pt_regs restore path.

sysret

The return. Restores rcx→RIP, r11→RFLAGS, CPL 0→3, jumps back to user space.

🎯 INTERACTIVE WORKSHOP: THE PHYSICAL SYSCALL DISPATCH

The Human Syscall Dispatcher

Student 01 · User Program

Holds a card labeled "read() syscall with buffer pointer." Approaches the CPU.

Student 02 · CPU Hardware

Holds a bell — rings it to represent the syscall instruction trap. Control passes to the dispatcher.

Student 03 · Dispatcher

Holds the syscall table — a printed list of numbers to function names. Looks up the request, routes to the right handler.

Students 04–06 · Handlers

Each represents a handler — read, write, fork. Each holds a symbolic "vault key" that allows execution.

Student 07 · Buffer Validator

Stands between dispatcher and handler. Verifies the buffer pointer is a valid user address before allowing the request through.

The Execution

User → CPU bell → dispatcher lookup → handler → buffer validation → execute → return result. Run through read, write, fork, mmap.

Pedagogic Takeaway: Physical intuition for the four-stage syscall pipeline. Validation (Student 07) is a critical part — every user-kernel interaction has this exact structure.

🏆 RETROSPECTIVE: SYLLABUS DISSECTION SUMMARY

Grand Lecture Summary

01

The system call interface is the only legitimate channel across the L02 hardware barrier. Every user-kernel interaction begins with a syscall instruction that traps from Ring 3 to Ring 0 in a single hardware cycle.

02

The kernel dispatches syscalls via a fixed integer key in rax and a sys_call_table array of function pointers. Arguments cross through a strict register convention (rdi, rsi, rdx, r10, r8, r9), and the return value comes back in rax.

The most security-critical part of every syscall handler is validating user-supplied pointers. Direct memcpy from user memory is a critical vulnerability; only copy_from_user/copy_to_user are safe.
