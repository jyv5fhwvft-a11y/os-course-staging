The Core Objective

Compare password-based and biometric authentication models, and identify an unalterable systemic vulnerability in each design.

The Problem Hook: L22 taught us that every /dev node, every /etc file, and every protected resource carries an ACL that says who may access it. But the system has a fatal blind spot: how does it know the caller is Alice and not an imposter claiming Alice's name? If an attacker can simply type "I am Alice" and receive her permissions, every ACL in the system is meaningless. Authentication is the doorway through which all access control must pass.

🎒 EVERYDAY SIMPLIFIED: THE THREE-FACTOR VAULT

The Three Factors Metaphor

🔐🔑🖐️
The Narrative

To enter a secure corporate vault, you must pass three gates: a password typed on a keypad (something you know), a physical brass key (something you have), and a fingerprint scan (something you are). Each gate proves a different dimension of your identity. An attacker who knows your password but does not have your physical key still fails.

Execution Path

These are the three classical authentication factor classes: Knowledge, Possession, Inherence. Each defeats a specific attack class that the others cannot.

Micro-Accessibility Context

Real systems rarely combine all three; two-factor is industry standard because it dominates the attacker cost curve at modest user friction.

🎒 EVERYDAY SIMPLIFIED: THE SHARED SECRET COMBINATION

The Password Metaphor

🔢🔐🔐
The Narrative

The bank assigns you a secret combination that only you know. The bank itself does not know the combination — it only knows a mathematical fingerprint of it, so that when you dial the combination, the bank can verify it matches its fingerprint without ever storing the actual dial positions.

Execution Path

Passwords are not stored in plaintext. The system stores a salted cryptographic hash of your password, and on each login attempt, hashes the input and compares the outputs.

Micro-Accessibility Context

The vulnerability is subtle: weak passwords and reused passwords are catastrophic, because anyone who discovers the plaintext (via a leak, phishing, or brute-force) can use it directly.

🎒 EVERYDAY SIMPLIFIED: THE UNIQUE RECIPE VARIANT

The Salted Hash Metaphor

🎂🧂🎂
The Narrative

Imagine two users, Alice and Bob, both use the exact same password — "hunter2." If the bank stored only the hash, both hashes would be identical, and an attacker with a rainbow table of common password hashes could crack both in one lookup. Instead, the bank sprinkles a random salt on each dish: Alice's password is hunter2 + aX9!q and Bob's is hunter2 + 7Lm@Z. The two hashes are completely different.

Execution Path

A salt is a random per-user string prepended to the password before hashing. Two users with the same password have different stored hashes.

Micro-Accessibility Context

This is the standard defense against rainbow-table attacks, and it is why /etc/shadow entries have a visible $id$salt$hash structure — the salt is right there in the record, but the hash of salt+password remains unreversable.

🎒 EVERYDAY SIMPLIFIED: THE IRREVOCABLE FINGERPRINT

The Biometric Vulnerability Metaphor

🖐️🔒❌
The Narrative

If someone steals your password, you change it — a new one works instantly. If someone steals your fingerprint template, you cannot change your fingerprint. The compromise is permanent — every future use of that template trusts the same irrevocable credential.

Execution Path

Passwords are revocable (change and reissue); biometrics are irrevocable. This asymmetry changes the entire risk calculus — biometric compromise implies lifelong vulnerability unless the entire biometric system is redesigned.

Micro-Accessibility Context

This is the deep security trade-off of biometrics: convenience and anti-spoofing strength on one hand, permanent irrevocability on the other.

🎒 EVERYDAY SIMPLIFIED: THE AUTHENTICATION DUALITY SUITE

The Summary Metaphor

✅ Revocable Corridor

Passwords and hardware tokens. Resettable, replaceable, changeable when compromised. The foundation of practical security.

❌ Irrevocable Corridor

Biometrics. Permanent, unique, unchangeable. Convenient but catastrophic when compromised.

The correct architecture blends them: use biometrics for local convenience, but require a revocable factor (password or hardware key) for high-security actions. Modern authentication is layered.

💻 SYSTEMS COHESION: KNOWLEDGE, POSSESSION, INHERENCE

The Three Authentication Factor Classes

🧠

Knowledge

Something you know.

Strengths: Universally available, instantly revocable, no hardware required.

Weaknesses: Phishing, shoulder surfing, keyloggers, weak password reuse.

Passwords · PINs · Security questions
📱

Possession

Something you have.

Strengths: Defeats remote attackers (physical presence required).

Weaknesses: Physical theft, SIM-swap attacks, token cloning (rare).

Hardware tokens · TOTP apps · Smart cards
🖐️

Inherence

Something you are.

Strengths: Cannot be forgotten or lost; defeats remote attacks entirely.

Weaknesses: Spoofing (photos, silicone prints), irrevocable compromise.

Fingerprints · Iris · Face ID · Voiceprint
Multi-Factor Authentication (MFA): Requires two or more distinct factor classes. An attacker who steals one factor still fails — they must defeat multiple independent channels simultaneously.
💻 SYSTEMS COHESION: THE STORED CREDENTIAL PIPELINE

Password Storage & Salted Hashing

1

User registers password P. The system generates a random per-user salt S (typically 16–32 bytes).

2

Compute H = hash(S || P). Using a strong hash function — SHA-256, or a password-specific algorithm like bcrypt, scrypt, or Argon2.

3

Store (S, H). In /etc/shadow (root-readable only). The entry is $6$S$H — algorithm ID, salt, and hash, separated by $.

4

Verification: On login, the system reads S from storage, computes H' = hash(S || submitted_P), and compares H' to H. Match = authenticated.

The one-way property: Even if /etc/shadow leaks, an attacker cannot compute P from H faster than brute-forcing all possible passwords. This is why strong passwords matter.
💻 SYSTEMS COHESION: THE PRECOMPUTED ATTACK

The Salt and Rainbow Table Defense

The Rainbow Table Attack

A precomputed database of hash(P) → P mappings for millions of common passwords.

Without salts, one table lookup cracks any leaked hash.

A single 10 GB rainbow table can crack hashes for millions of common passwords in milliseconds.

The Salt Defense

Without salt: Two users with password "hunter2" both have hash H₀. One rainbow-table lookup cracks both.

With salt: Alice's entry hashes saltA||hunter2; Bob's hashes saltB||hunter2. Neither appears in the rainbow table.

The attacker must now crack each user's hash independently — O(N) work per user.

The Verdict: Salts do not defend against weak passwords (an attacker will still crack "password123" quickly), but they defend against batch cracking — one leak no longer compromises every user with a common password.
💻 SYSTEMS COHESION: THE BIOMETRIC VECTOR MATCH

Biometric Authentication Pipeline

The Biometric Pipeline

1. Capture: Sensor captures raw biometric data (fingerprint ridge map, iris pattern, facial geometry).

2. Feature extraction: A specific feature vector is extracted — for fingerprints, a set of minutiae points (ridge endings, bifurcations) and their relative positions.

3. Template storage: The extracted feature vector (not the raw scan) is stored. For a 1024-bit iris template, this is ~128 bytes per user.

4. Matching: New scan → features extracted → compared to stored template (Hamming distance for iris, minutiae count for fingerprints).

5. Threshold: Match score above threshold = authenticated.

The Fundamental Difference

Passwords are exact matches. Biometrics are statistical matches — due to sensor noise, angle variation, and physiological drift.

This introduces false accepts (wrong person granted access) and false rejects (right person denied) as permanent risks.

Biometric templates can be leaked the same as password hashes — but unlike passwords, the compromised "password" is your fingerprint, which you cannot change.

💻 SYSTEMS COHESION: THE IRREVOCABILITY CURSE

The Revocability Asymmetry

🔑 Password (Revocable)

· Can be reset instantly

· Can be lost (forgotten)

· Can be stolen (leaked)

· If leaked, can be changed

· Often reused across services

🖐️ Biometric (Irrevocable)

· Cannot be reset

· Cannot be lost (always with you)

· Can be stolen (spoofing)

· If leaked, cannot be changed

· Shared across all services using that template

The Deep Problem: If your biometric template is compromised, every system that uses that biometric — even systems you have never logged into yet — trusts the compromised template. You cannot "change your fingerprint" without changing your physical body.
🔗 SYSTEM PIPELINE: RELIES ON IDENTITY VERIFICATION

Core System Cohesion — Relies On L22

ACLs Need Identity

Every ACL entry contains a subject identifier — Alice, Bob, Charlie. But that identifier is meaningless unless the system can verify the caller is that subject. Authentication supplies the verified identity that L22's ACL check consumes.

The Credential Struct

After L23 authentication succeeds, the kernel populates the process's credential struct (uid, gid, supplementary groups) — which is the exact input that L22's ACL check compares against the file's ACL.

The Architectural Bond

Authentication and access control are inextricably linked: one proves who you are, the other decides what you may do. Neither is useful without the other.

Feeds Into L24–L27

Every subsequent Module 7 lecture presumes a working authentication substrate. L24 (exploits) attacks the parsers of auth systems. L25 (crypto) protects auth credentials in transit. L27 (isolation) allows different processes to have different authenticated identities.

🔗 SYSTEM PIPELINE: FEEDS INTO EXPLOITS AND CRYPTO

Core System Cohesion — Feeds Into L24 & L25

L24 (Buffer Overflows)

Password input fields, biometric template comparisons, and token verifiers are all high-risk C code that can be exploited via unchecked inputs. Authentication is one of the most common attack surfaces for memory-safety bugs.

L25 (Encryption)

Passwords traverse the network from client to server. Without TLS encryption, they are visible to any network snooper. Authentication requires encryption as a transport-layer defense — the two are inseparable.

The Chain

Identity (L23) → exploit defenses (L24) → encrypted transport (L25) → network security (L26) → isolation (L27). Each layer presumes the one before it.

Real-World Consequence

Every breach that involves "credentials were leaked" traces back to the failures this lecture describes: weak passwords, missing salts, unencrypted transport, or compromised biometrics.

🔍 COMPREHENSIVE CRITIQUE: KERNEL AUTH ARCHITECTURES

Authentication Across the Five Paradigms

Monolithic Authentication

Authentication is handled by a central in-kernel or privileged daemon (PAM, systemd-logind). All logins route through it. Fast, central, but a compromise of the auth stack compromises the entire system.

Microkernel Authentication

Authentication is a user-space service accessed via IPC. Each app that needs to authenticate contacts the auth server. The auth server holds credentials — never the kernel. Isolated and replaceable, but every login involves IPC message round-trips.

Layered Authentication

Strict separation: hardware-backed credential storage → kernel credential manager → user-space PAM stack. Each layer enforces a specific concern without overlapping. Mirrors modern systems-on-chip with TPM-backed credential storage.

Modular Authentication

PAM (Pluggable Authentication Modules) is the archetype — password auth, token auth, biometric auth are all pluggable modules dynamically composed per service. Swap authentication method without recompiling the kernel.

Hybrid Authentication

Hardware security modules (TPM 2.0, Apple Secure Enclave) hold root keys in silicon, while the OS auth stack handles day-to-day password verification. Cryptographic keys never leave the security chip — but the OS still orchestrates the login flow.

🏷️ SYSTEM LEXICON: MASTERING THE AUTHENTICATION VOCABULARY

Base Authentication Terms

Term 01 · Authentication Factor

An explicit operational category used to verify a user's digital identity boundaries — one of Knowledge (something the user knows, like a password), Possession (something the user has, like a hardware token), or Inherence (something the user is, like a fingerprint). Each factor defeats a specific attack class that the others cannot.

(The three different ways to prove you are who you say you are.)

Term 02 · Salted Hash

Appending a random sequence of characters (the salt) to a user password before passing it through a cryptographic one-way hashing function, neutralizing dictionary-lookup attacks and rainbow-table precomputation by making each user's hash unique even when they share the same underlying password.

(A unique random topping added to each dish so that two identical recipes produce completely different dish IDs.)

🏷️ SYSTEM LEXICON: MASTERING THE AUTHENTICATION VOCABULARY

Advanced Authentication Terms

Term 03 · Multi-Factor Authentication (MFA)

Requiring a user to validate two or more distinct authentication categories (knowledge + possession, knowledge + inherence, etc.) before granting entry access, ensuring that compromising a single channel is insufficient for unauthorized access. Two-factor authentication (2FA) is the most common deployment.

(The bank requiring both your password AND your physical key.)

Term 04 · Rainbow Table

A precomputed database mapping common password hashes back to their plaintext passwords, used to crack leaked credential stores efficiently; defeated by the salted-hash technique, which ensures every user's stored hash is unique even for identical passwords. Modern tables can be hundreds of GB in size.

(A pre-built reverse-lookup dictionary for common password hash values.)

Term 05 · Revocability

The property of a credential that allows it to be invalidated and replaced after compromise; passwords and hardware tokens are revocable, biometric templates are not — creating a fundamental security asymmetry that shapes the entire biometric risk calculus. Revocable factors must be present in any high-security architecture.

(You can change a password, but you cannot change your fingerprint.)

💻 CODE DISSECTION: C SALTED HASH SIMULATOR

Simulating Salted Password Hashing in C

// Simulating salted password hashing and verification in C
// Compile: gcc -o salt salt.c && ./salt
#include <stdio.h>
#include <string.h>
#include <stdlib.h>
#include <time.h>

// WARNING: This is a SIMPLIFIED demonstration hash.
// NEVER use a toy hash in production. Use bcrypt, scrypt, or Argon2.
unsigned long demo_hash(const char* input) {
    unsigned long h = 5381;
    while (*input) {
        h = ((h << 5) + h) + (unsigned char)*input++;
    }
    return h;
}

void generate_salt(char* salt, int length) {
    const char charset[] =
        "abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789";
    for (int i = 0; i < length - 1; i++) {
        salt[i] = charset[rand() % (sizeof(charset) - 1)];
    }
    salt[length - 1] = '\0';
}

// Registration: hash salt || password and store the result
void register_user(const char* password, char* stored_salt,
                   unsigned long* stored_hash) {
    generate_salt(stored_salt, 17);   // 16-character random salt
    char combined[256];
    snprintf(combined, sizeof(combined), "%s%s", stored_salt, password);
    *stored_hash = demo_hash(combined);
    printf("[REGISTER] salt=%s  hash=%lu\n", stored_salt, *stored_hash);
}

// Login: rehash submitted password with stored salt, compare
int verify_login(const char* password, const char* stored_salt,
                 unsigned long stored_hash) {
    char combined[256];
    snprintf(combined, sizeof(combined), "%s%s", stored_salt, password);
    unsigned long attempt = demo_hash(combined);
    printf("[LOGIN]    attempt=%lu  expected=%lu -> %s\n",
           attempt, stored_hash, (attempt == stored_hash) ? "ACCEPT" : "REJECT");
    return attempt == stored_hash;
}

int main() {
    srand((unsigned)time(NULL));

    char salt1[17], salt2[17];
    unsigned long hash1, hash2;

    // Two users with the SAME password "hunter2"
    register_user("hunter2", salt1, &hash1);
    register_user("hunter2", salt2, &hash2);

    printf("\nSame password, different salt, different hash:\n");
    printf("  Hash1: %lu\n", hash1);
    printf("  Hash2: %lu\n", hash2);
    printf("  %s\n", hash1 != hash2 ?
           "Rainbow table attack DEFEATED" :
           "BUG: hashes are equal!");

    printf("\nAttempting login for user 1:\n");
    verify_login("hunter2", salt1, hash1);       // correct
    verify_login("wrongpass", salt1, hash1);     // incorrect
    return 0;
}

Use code with caution.

💻 CODE DISSECTION: TRACING CREDENTIAL VERIFICATION

Walking the Salted Hash Trace

generate_salt(stored_salt, 17)

The critical defense against rainbow tables. Generates a random 16-character string per user. In real systems, the salt is 16–32 bytes of cryptographically secure randomness.

snprintf(combined, ..., "%s%s", salt, password)

Concatenates salt + password in that order. This is the exact defense L23 describes: hash(salt || password) produces a completely different hash for hunter2 per user.

demo_hash(combined)

Applies the hash function. In production, this would be bcrypt, scrypt, or Argon2 — deliberately slow hash functions designed to make brute-force attacks expensive even for leaked hashes.

Two user traces

Both users have password "hunter2," but salt1 ≠ salt2. Therefore demo_hash(salt1||hunter2) ≠ demo_hash(salt2||hunter2). An attacker with a precomputed rainbow table for "hunter2" gets zero hits — neither hash appears in the table.

verify_login(...)

The login path: retrieves the stored salt from the database, hashes the submitted password with that salt, and compares. Match = user authenticated. Same hash function, same salt, same result — but only if the input password is correct.

The Attack Cost

With a leaked /etc/shadow and 1 million distinct salts, an attacker must brute-force each user's hash independently. Cost = O(users × search_space) instead of O(search_space). A 1000× increase in attack cost.

🎯 INTERACTIVE WORKSHOP: THE PHYSICAL MFA SIMULATION

The Three-Factor Vault Showdown

Student 01 · The Vault Guard

Stands at the front with three checkpoints between the "user area" and the "vault area." Determines how many factors are required per round.

Student 02 · The User

Must reach the vault. Holds three factor cards: a password card, a hardware token card, and a biometric card.

Students 03–05 · The Factors

Each is a checkpoint guard. Student 03 checks the password card; Student 04 checks the hardware token; Student 05 checks the biometric card.

Round 1 · Single Factor

Vault Guard allows entry with ANY single factor. User passes with only the password card. Note how easy this is to bypass.

Round 2 · Two Factors (MFA)

Guard requires two factors. User passes with password + token, but fails with password alone. Run the "attacker" scenario with only the password.

Round 3 · Three Factors

Guard requires all three. User must possess every factor card. Now try attacker scenarios: only password, password + token, etc. Each additional factor multiplies the attacker's burden.

🏆 RETROSPECTIVE: SYLLABUS DISSECTION SUMMARY

Grand Lecture Summary

01

Authentication verifies identity along three distinct factor channels — knowledge, possession, and inherence. Real systems combine them (MFA) so that compromising one channel does not breach the entire account.

02

Passwords are stored as salted cryptographic hashes, never in plaintext. The salt defeats rainbow tables by ensuring two users with identical passwords have completely different stored hashes — but strong passwords and slow hash functions remain essential to defeat brute force.

03

Biometrics are irrevocable — an inherent asymmetry versus passwords. A leaked fingerprint template cannot be changed. This is why strong biometric systems always pair the biometric with a revocable factor (PIN, password, or hardware token) so that compromising the biometric alone is insufficient.
