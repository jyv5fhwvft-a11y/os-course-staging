The Core Objective

Classify a variety of physical hardware items into Block, Character, or Network device driver categories, and trace how a user-space file command routes to a hardware controller via virtual filesystem file operations.

The Problem Hook: Every peripheral manufacturer builds hardware with completely different electrical and protocol characteristics. Logitech's keyboard speaks one register language; Intel's network chip speaks another; Samsung's NVMe SSD speaks a third. The OS kernel cannot contain unique, bespoke code for 10,000 different models — and it certainly cannot ship a new kernel every time a new device is released. How do we build a single, unified device abstraction layer that handles fast hardware streaming without rewriting the kernel for every new toaster?

🎒 EVERYDAY SIMPLIFIED: THE UNIVERSAL WALL OUTLET

The Driver Metaphor

🔌🔋💡
The Narrative

The wall outlet does not know or care what you plug in. It presents a simple, standardized interface and delivers power uniformly. A toaster, a lamp, and a laptop look identical to the outlet. Inside each device is a small adapter that converts the standardized power into whatever internal form that device actually needs.

Execution Path

A device driver is that adapter plug. To the operating system, every device looks like a standard file that handles open(), read(), write(), and close(). The driver translates those generic operations into the unique language of that specific hardware chip.

Micro-Accessibility Context

This maps directly to struct file_operations — a C function-pointer table that presents a uniform interface regardless of the underlying hardware.

🎒 EVERYDAY SIMPLIFIED: THE LIBRARY AND THE FAUCET

The Block vs Character Metaphor

📚🚰
The Narrative

A Block Device is like a library bookshelf: you can request any book at any time, in any order, by its shelf coordinate. Seek, jump backward, read chapter 5 before chapter 1 — all fine. A Character Device is like a water faucet: drops arrive sequentially, the flow is continuous, and once you have caught a drop you cannot go back and un-catch it. There is no "seek to drop #12."

Execution Path

This distinction shapes how the kernel interfaces with the driver: block devices support random access and caching layers; character devices support only sequential streaming reads/writes.

Micro-Accessibility Context

Both are exposed via /dev, but their behavior differs fundamentally at the driver interface level.

🎒 EVERYDAY SIMPLIFIED: THE MAIL CARRIER

The Network Device Metaphor

📬✉️🚚
The Narrative

A Network Device is neither a bookshelf nor a faucet — it is a mail carrier who delivers self-contained packets. Each packet has a destination address, a payload inside, and a routing envelope. You do not address individual bytes to the carrier — you hand over complete envelopes, and the carrier delivers them to their destinations.

Execution Path

Network devices speak in frames and packets, not in byte streams. They are exposed through the socket API (socket(), send(), recv()) rather than through read()/write() on /dev nodes.

Micro-Accessibility Context

This is why /dev does not contain traditional character/block nodes for network interfaces — they live in a separate namespace (/sys/class/net).

🎒 EVERYDAY SIMPLIFIED: STREET ADDRESS AND APARTMENT NUMBER

The Major/Minor Metaphor

🏢🚪🔢
The Narrative

A major device number identifies the driver — the building. A minor device number identifies the specific device instance — the apartment inside. One driver can manage many physical devices (eight hard drives, four network ports), each with its own minor number.

Execution Path

When the kernel receives open("/dev/sda1"), it reads the device node's st_rdev field to extract major/minor numbers, looks up the registered driver for that major, and dispatches the open call with the minor number.

Micro-Accessibility Context

This is the routing mechanism that lets a single driver service many devices through the same abstraction layer.

🎒 EVERYDAY SIMPLIFIED: THE ABSTRACTION UNIFORMITY SUITE

The Summary Metaphor

❌ Raw Hardware Chaos

10,000 devices, each with its own register layout, protocol, and interrupt behavior. Every app would need to understand every hardware device it uses.

✅ Unified /dev Files

Three driver categories — Block, Character, Network — all exposed through a single, uniform file-based interface. Chaos collapses into order.

The entire abstraction strategy reduces the world of 10,000 different hardware devices to just three driver categories — all exposed through a single, uniform file-based interface. This is the OS's central scalability insight: define the interface once, implement it many times, and manage all devices the same way.

💻 SYSTEMS COHESION: BLOCK, CHARACTER, AND NETWORK

The Three Hardware Categories

💾

Block Devices

Read/write in fixed-size, addressable blocks (512 B to 4 KB). Support random access and seek. Managed by the block I/O subsystem (L16–L19).

/dev/sda, /dev/nvme0n1, /dev/loop0
⌨️

Character Devices

Read/write as continuous sequential byte streams. No random access, no seek. Managed by the char device subsystem.

/dev/tty, /dev/ttyS0, /dev/input/event0
🌐

Network Devices

Read/write as framed packets with headers and addresses. No file semantics, no seek. Managed by the network stack.

/sys/class/net/eth0, /sys/class/net/wlan0
The Verdict: Three categories, one abstraction layer (struct file_operations) with category-specific operations underneath. Network devices are the single named exception to "everything is a file."
💻 SYSTEMS COHESION: FUNCTION-POINTER POLYMORPHISM

The struct file_operations Dispatch Table

struct file_operations { ssize_t (*read) (struct file *, char __user *, size_t, loff_t *); ssize_t (*write) (struct file *, const char __user *, size_t, loff_t *); int (*open) (struct inode *, struct file *); int (*release) (struct inode *, struct file *); long (*ioctl) (struct file *, unsigned int, unsigned long); loff_t (*llseek) (struct file *, loff_t, int); // ... plus dozens more };

The Dispatch Rule

Every device driver registers a struct file_operations instance when it initializes.

When user code calls read(fd, buf, n), the VFS layer looks up the file's associated file_operations table, then calls the driver's read() function through the pointer.

The Verdict

This is the central scalability mechanism: the kernel does not need to know what each driver does — only that it implements the interface.

C-language polymorphism through function pointers.

💻 SYSTEMS COHESION: DRIVER AND INSTANCE IDENTIFICATION

The Major/Minor Device Number System

Major (12 bits)
+
Minor (20 bits)
A dev_t is a 32-bit integer
# Example: /dev/sda1 has major=8 (SCSI disk driver), minor=1 (first partition of first SCSI disk)

The Device Number Structure

Major (12 bits): Identifies the driver. One major number per driver. Linux allocates major numbers from a global registry.

Minor (20 bits): Identifies the specific device instance. A single SCSI driver with major 8 can manage up to 2²⁰ minor numbers — millions of disk partitions.

Example Decode

When you ls -l /dev/sda1 and see brw-rw---- 1 root disk 8, 1, this means:

· Major 8: SCSI disk driver

· Minor 1: First partition of first SCSI drive

Major/minor numbers are how the kernel routes a syscall to the right driver and instance.

💻 SYSTEMS COHESION: THE DEVICE FILE ON DISK

The Complete /dev Node Anatomy

brw-rw---- 1 root disk 8, 1 Mar 15 10:30 /dev/sda1

Device Node Anatomy

File type: b (block), c (character) — visible as the first character of ls -l.

Permissions: Standard Unix read/write/execute bits — the security enforcement mechanism for Module 7.

st_rdev: The device number (major + minor) stored in the inode.

No data blocks: Device files have zero data blocks — reads and writes go through the driver, not into inode-pointed storage.

The Elegance

Device nodes reuse the entire Module 5 file system infrastructure — directories, inodes, permissions — but replace the data-block pointer tree with a device-number dispatch pointer.

The same open() syscall works on files AND devices.

The kernel simply checks the file type in the inode and routes accordingly.

💻 SYSTEMS COHESION: THE DRIVER LIFECYCLE

Driver Registration and the file_operations Hookup

The Registration Sequence

1. Load: The module's init function runs — either at boot or on insmod.

2. Allocate major: The driver calls register_chrdev() or alloc_chrdev_region() to claim a major number.

3. Register file_operations: The driver publishes its function-pointer table to the kernel's driver registry.

4. Create /dev node: Usually via udev — when the device is detected, udev creates the node with the right major/minor.

5. Handle syscalls: The kernel's VFS dispatch layer routes reads/writes to the driver functions.

6. Unload: On rmmod or device removal, the driver releases the major number and its node is removed.

The Modular Model

This is the modular end of the kernel architecture spectrum — the driver is a loadable plug-in implementing the abstract file_operations interface.

Linux ships with hundreds of driver modules that can be loaded on demand. When you plug in a USB device, the kernel identifies its vendor/device ID, looks up the matching driver module, loads it, and calls its init function.

This is the entire modern Linux driver model.

🔗 SYSTEM PIPELINE: RELIES ON VFS FILE ABSTRACTION

Core System Cohesion — Relies On L17

The Same Path Resolution

A /dev node is opened through the exact same VFS path resolution process as a regular file: open("/dev/sda1") walks / → dev → sda1, hits an inode with S_IFBLK, allocates a file descriptor, and returns the fd.

The Only Difference

The only difference from a regular file is what happens after open: the read/write syscalls dispatch to the driver's file_operations table instead of the filesystem's block-pointer tree.

The Architectural Bond

L21 is entirely built on L17's file abstraction. The VFS layer is the universal frontend; the driver is the specific backend. Same interface, different implementation.

Feeds Into Module 7

By exposing every device as a file, the kernel can enforce security with ordinary file permission bits (L17's inode metadata). The /dev node ACLs from L22 will protect physical devices.

🔗 SYSTEM PIPELINE: FEEDS INTO ACCESS CONTROL

Core System Cohesion — Feeds Into Module 7

File Permission Bits

Access to /dev/sda1 is controlled by chmod and chown — no special security mechanism is needed for the physical disk. The same ACL system from L17 protects every device.

The Elegance

This is the elegance of the "everything is a file" model: adding a new device requires no new security mechanism. The existing file permission infrastructure applies uniformly.

Module 7 Preview

L22 (access control) will formalize this. L23 (authentication) will gate access to privileged devices. L27 (isolation) will use device namespaces to virtualize /dev for containers.

The Chain

L17 (VFS) → L21 (drivers) → L22 (ACLs) → L23 (auth) → L27 (isolation). Every layer builds on the ones below.

🔍 COMPREHENSIVE CRITIQUE: DRIVER ARCHITECTURES

Driver Strategies Across the Five Paradigms

Monolithic Drivers

Drivers are compiled into the kernel or loaded as kernel modules (Linux, FreeBSD). Execute at Ring 0 with full privilege. Direct register access via inb/outb/readl/writel. Fastest path, but a buggy driver can crash the kernel.

Microkernel Drivers

Drivers run as user-space servers (MINIX 3, seL4). Receive hardware access via privileged IPC and privileged instructions — the kernel delivers IRQ events and maps MMIO regions on request. Slower but fully isolated — a buggy driver cannot crash the kernel.

Layered Drivers

Strict HAL → device class → concrete driver hierarchy. Windows uses this: HAL abstracts CPU/motherboard, ACPI abstracts devices, KMDF and UMDF frameworks provide layered driver templates.

Modular Drivers

Loadable Kernel Modules (LKMs) — Linux's model. Drivers are .ko files that can be loaded and unloaded at runtime via insmod/rmmod/modprobe. Same privilege as monolithic but far more flexible.

Hybrid Drivers

Critical drivers (disk, network) in-kernel for latency; user-space drivers via FUSE, uio, or SPDK for research, custom, or high-throughput hardware. Modern Linux is functionally hybrid: NVMe drivers can run in-kernel OR bypass through SPDK.

🏷️ SYSTEM LEXICON: MASTERING THE DRIVER VOCABULARY

Base Driver Terms

Term 01 · Device Driver

A specialized kernel software module that bridges the gap between the generic operating system file operation interface and the custom electrical registers of a specific hardware peripheral, translating open/read/write/ioctl syscalls into hardware-specific register operations. Runs at Ring 0 privilege on monolithic kernels, or as user-space servers on microkernels.

(The universal wall outlet adapter that turns standard power into the specific format a device needs.)

Term 02 · Block Device

A class of hardware components that read and write data in fixed-size, addressable block sectors (typically 512 B to 4 KB), natively supporting random-access seeks; managed by the block I/O subsystem and cached by the page cache. Every modern HDD and SSD is a block device.

(The library bookshelf — any book at any shelf position, any time.)

🏷️ SYSTEM LEXICON: MASTERING THE DRIVER VOCABULARY

Advanced Driver Terms

Term 03 · Character Device

A class of hardware components that deliver data as a non-addressable, continuous stream of sequential bytes — no seek, no random access; each read consumes bytes in arrival order. Examples include keyboards, mice, serial ports, and terminals. Character devices cannot be cached by the page cache because there is no position to cache.

(The water faucet — drops arrive in sequence, no rewind.)

Term 04 · file_operations Struct

A kernel data registry containing function pointers that route standard system calls (open, read, write, release, ioctl, llseek, etc.) directly to their matching hardware driver backend implementations. Each device driver registers one instance, providing the kernel's polymorphic dispatch mechanism.

(The outlet's internal wiring schematic — connects each prong to the right current path.)

Term 05 · Major/Minor Numbers

A 32-bit device identifier split into a 12-bit major number (identifying the driver) and a 20-bit minor number (identifying the specific instance of that device). The kernel routes syscalls to the correct driver and instance by decoding these numbers from the device node's inode.

(The street address — which building, which apartment.)

💻 CODE DISSECTION: C CHARACTER DRIVER SKELETON

A Minimal Linux Character Driver

// Minimal Linux character driver demonstrating file_operations dispatch
#include <linux/fs.h>
#include <linux/module.h>
#include <linux/uaccess.h>
#include <linux/init.h>

static char driver_buffer[256] = "Hello from the driver!\n";
static int open_count = 0;

// Called when user space does open("/dev/mydev", O_RDONLY)
static int my_dev_open(struct inode *inode, struct file *file) {
    open_count++;
    printk(KERN_INFO "mydev: open() called (count=%d)\n", open_count);
    return 0;
}

// Called when user space does read(fd, buf, n)
static ssize_t my_dev_read(struct file *file, char __user *buf,
                           size_t count, loff_t *ppos) {
    if (*ppos >= sizeof(driver_buffer))
        return 0;  // EOF
    size_t to_copy = min((size_t)(sizeof(driver_buffer) - *ppos), count);
    if (copy_to_user(buf, driver_buffer + *ppos, to_copy))
        return -EFAULT;
    *ppos += to_copy;
    return to_copy;
}

// Called when user space does write(fd, buf, n)
static ssize_t my_dev_write(struct file *file, const char __user *buf,
                            size_t count, loff_t *ppos) {
    size_t to_copy = min((size_t)sizeof(driver_buffer), count);
    if (copy_from_user(driver_buffer, buf, to_copy))
        return -EFAULT;
    printk(KERN_INFO "mydev: wrote %zu bytes\n", to_copy);
    return to_copy;
}

// Called when user space does close(fd)
static int my_dev_release(struct inode *inode, struct file *file) {
    printk(KERN_INFO "mydev: close() called\n");
    return 0;
}

// The dispatch table — this struct is the ENTIRE driver interface
static struct file_operations my_dev_fops = {
    .owner   = THIS_MODULE,
    .open    = my_dev_open,
    .read    = my_dev_read,
    .write   = my_dev_write,
    .release = my_dev_release,
};

static int __init my_dev_init(void) {
    register_chrdev(240, "mydev", &my_dev_fops);  // major=240
    printk(KERN_INFO "mydev: registered with major 240\n");
    return 0;
}

static void __exit my_dev_exit(void) {
    unregister_chrdev(240, "mydev");
    printk(KERN_INFO "mydev: unregistered\n");
}

module_init(my_dev_init);
module_exit(my_dev_exit);
MODULE_LICENSE("GPL");

Use code with caution.

💻 CODE DISSECTION: TRACING DRIVER FUNCTION DISPATCH

Walking the Dispatch Trace

register_chrdev(240, "mydev", &my_dev_fops)

The registration step. The driver claims major number 240 and publishes its file_operations table to the kernel registry. This is the entire registration — one function call.

my_dev_open

Called on open("/dev/mydev", ...). The kernel walks / → dev → mydev, finds the inode with major 240, looks up the driver in the registry, and calls my_dev_open via the open function pointer.

my_dev_read

Called on read(fd, buf, n). The VFS looks up file->f_op->read, finds my_dev_read, and calls it. Note copy_to_user() — the driver cannot memcpy directly because user space and kernel space have separate address spaces (per L02).

my_dev_write

Called on write(fd, buf, n). Symmetrically uses copy_from_user() to safely bring user bytes into the kernel.

my_dev_release

Called on close(fd). The kernel decrements the file descriptor's reference count and calls the release handler when the count reaches zero.

my_dev_fops

The file_operations table itself. This single struct is the driver. If any function pointer is NULL, the corresponding operation returns -EINVAL. This is the polymorphism: the same syscall interface routes to completely different driver implementations.

🏆 RETROSPECTIVE: SYLLABUS DISSECTION SUMMARY

Grand Lecture Summary

01

The kernel divides every hardware device into one of three categories — Block, Character, or Network — each with its own access semantics. The first two are exposed as files in /dev; the third (network) breaks the "everything is a file" rule because it speaks in packets, not bytes.

02

A device driver is fundamentally a struct file_operations — a C-language function-pointer table that implements the uniform syscall interface (open, read, write, release, ioctl). The kernel does not know what each driver does; only that it implements this interface.

03

Major/minor numbers are the dispatch key: major identifies the driver, minor identifies the instance. The st_rdev field in the /dev inode is decoded by the VFS and used to route syscalls to the correct driver's file_operations table.
