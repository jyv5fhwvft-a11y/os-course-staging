The Core Objective

Explain the exact operational lifecycle difference between cloning an address space (fork) and overriding an address space (exec), and trace register states during a context switch.

The Problem Hook: Unix has exactly two system calls that create or transform processes: fork() — which clones an existing process into an identical child — and exec() — which replaces a process's entire address space with a new program. Together, they are the foundation of every shell, every IDE, every server daemon, and every container runtime in existence. How do these two syscalls compose to launch any process on Earth?

🎒 EVERYDAY SIMPLIFIED: THE PERFECT RUNNER CLONE

The fork() Metaphor

🏃‍♂️🏃‍♂️⚡
The Narrative

Imagine a runner on a track, and suddenly a perfect clone materializes beside them. The clone has the exact same memories, same muscle memory, same position, and same script. From that instant onward, both runners may take different paths around the track — one turns left, one turns right. But at the moment of the clone, they are indistinguishable.

Execution Path

fork() creates a new process (the child) that is initially an exact copy of the parent — same memory contents, same registers, same file descriptors, same program counter. Both continue from the instruction after fork(), but each follows a different branch.

Micro-Accessibility Context

Two processes that are identical at creation and diverge only by their subsequent code path.

🎒 EVERYDAY SIMPLIFIED: THE NEW SCRIPT OVERWRITE

The exec() Metaphor

📜✂️📜
The Narrative

exec() is not about creating a clone — it is about replacing the script. The runner's body stays the same (same PID, same identity), but the script they follow — the instructions they execute, the data they read, the functions they call — is completely replaced. The old story is gone; a new one begins.

Execution Path

exec() calls replace the process's address space (Text, Data, Heap, Stack) with a new executable's contents. The program counter resets to the new binary's entry point.

Micro-Accessibility Context

fork creates a new process; exec transforms an existing process into a different program.

🎒 EVERYDAY SIMPLIFIED: THE RUNNER'S BATON PASS

The Context Switch Metaphor

🏃🤝🏃
The Narrative

A single track has only one runner at a time (one CPU core). To let multiple runners use it, the referee forces a rotation: runner A pauses mid-stride, the referee writes down exactly where they were, hands the baton to runner B, and later — when B pauses — hands the baton back to A, who resumes from exactly where they left off.

Execution Path

A context switch is the referee's pause-and-resume operation. The kernel saves the outgoing process's registers into its PCB and loads the incoming process's registers from its PCB.

Micro-Accessibility Context

Context switching is the invisible operation that makes multitasking possible — it costs real time, and happens thousands of times per second.

🎒 EVERYDAY SIMPLIFIED: THE UNIVERSAL TICKET

The fork + exec Pattern Metaphor

🎫🚀🔧
The Narrative

To launch any program, Unix uses a two-step pattern: first, fork() a worker (making an identical clone of yourself); then, in the worker, exec() their brain with the new program. The original worker is unchanged; the new worker is now the new program. Every time you run ls, grep, python, or chrome, the shell does exactly this.

Execution Path

The canonical Unix process-launching pattern: pid = fork(); if (pid == 0) execve(...); else wait(pid);. This is what system(), popen(), posix_spawn(), and every shell all do internally.

Micro-Accessibility Context

The universal mechanism by which any program becomes another program on Unix.

🎒 EVERYDAY SIMPLIFIED: THE FORK-AND-EXEC SUITE

The Summary Metaphor

🌱 fork creates

New process. Isolated from parent. Same state at the moment of creation.

🔄 exec transforms

Same process. New program. Completely new address space.

fork() provides isolation (the child cannot crash the parent); exec() provides transformation (the child becomes a new program). Together, they enable the shell, the daemon, the container — every process-launching mechanism in existence.

💻 SYSTEMS COHESION: THE PROCESS DUPLICATION

fork() — The Clone Operation

Parent Process (PID 1234)
pc = next_instruction_after_fork
↓ fork() ↓
Parent (PID 1234)
fork() returns child_PID (=5678)
Child (PID 5678)
fork() returns 0

The fork() Pipeline

1. Syscall trap: User calls fork(). libc loads rax=57, executes syscall.

2. PCB allocation: Kernel allocates new task_struct, copies every field from parent.

3. Address space clone: Page tables copied (COW — see Slide 09).

4. FD copy: FD table duplicated. Each FD shares the same struct file (same offset).

5. Scheduler enqueue: Child placed in Ready state, added to run queue.

6. Return value distinction: Parent gets child's PID; child gets 0.

The Verdict

fork() produces two nearly-identical processes that diverge only by their subsequent code execution.

It's the most elegant process-creation primitive ever designed — and it's been in Unix since 1970.

The only observable difference: the return value in rax (child's PID > 0 in parent; 0 in child).

💻 SYSTEMS COHESION: THE SHARED-PAGE OPTIMIZATION

Copy-on-Write (COW) — The Paging Miracle

The COW Mechanism

After fork: Parent and child page tables point to the same physical frames. Both marked read-only.

On read: Either process reads normally — shared frame is fine for read access.

On write: The MMU traps with a page fault when either process attempts to write. The kernel's page fault handler recognizes the COW case, allocates a new physical frame, copies the old frame's contents into it, and updates the writing process's page table.

After the copy: The writer has its private writable frame; the other process still has the original read-only frame.

The Cost Analysis

Without COW: fork() would always copy the entire address space — costly for large processes. Forking a 2 GB Chrome process would require 2 GB of physical RAM.

With COW: fork() is nearly free (just page table copies). Only written pages are ever physically duplicated.

This is why modern shell launches, server forks, and container creations are instant even on multi-GB processes.

💻 SYSTEMS COHESION: THE PROGRAM REPLACEMENT

exec() — The Address Space Overwrite

The exec() Pipeline

1. Syscall trap: User calls execve(path, argv, envp). Kernel traps into Ring 0.

2. Binary loading: Kernel reads the executable from disk. Parses ELF header, identifies Text/Data segments, entry point.

3. Old address space destruction: Existing Text, Data, Heap, Stack discarded. Page table entries invalidated.

4. New segments mapped: New binary's segments mapped. New stack allocated with argv and envp. New PC set to ELF entry.

5. Registers reset: All general-purpose registers reset. PC points to new _start.

6. Continue execution: Kernel returns not to caller, but to new program's entry.

The Verdict

exec() is not a return-from-syscall — it is an entry-into-a-new-program.

The original code that called execve() never resumes. If execve() returns at all, it returns only with an error (file not found, permissions, etc.) — success means the caller is gone.

Successful exec = no return. Failed exec = returns error.

💻 SYSTEMS COHESION: THE SHELL'S CORE ALGORITHM

The Canonical fork + exec Launch Pattern

// Every Unix shell, every system() call, every container runtime uses this
pid_t pid = fork();           // 1. Clone
if (pid < 0) {
    perror("fork failed");
    exit(1);
} else if (pid == 0) {
    // 2. Child branch — transform into the new program
    char *args[] = { "/bin/ls", "-l", NULL };
    execv(args[0], args);
    // If exec succeeds, this line NEVER executes.
    // If we reach here, exec failed.
    perror("exec failed");
    _exit(1);
} else {
    // 3. Parent branch — wait for child to complete
    int status;
    waitpid(pid, &status, 0);
    printf("Child %d completed with status %d\n", pid, status);
}

This pattern is THE Unix process-launching idiom. Every system("ls -l"), every popen("grep ..."), every docker run involves some variation.

💻 SYSTEMS COHESION: THE COMPLETE REGISTER EXCHANGE

Context Switch — The Full PCB Save/Restore

The Context Switch Sequence (x86-64)

1. Trigger: Timer interrupt, syscall, or blocking event → kernel considers a switch.

2. Save A: Kernel saves rip (PC), rsp (stack pointer), general regs (rax, rbx, rcx, rdx, rsi, rdi, rbp, r8–r15), flags register, FPU state.

3. Pick B: Scheduler chooses next process (L07–L08).

4. Load B: Kernel pops saved values from B's PCB into the CPU.

5. Page table switch (if needed): Update cr3 to B's page tables → TLB flush (L12).

6. Resume: Kernel's iret/sysexit returns from interrupt, resuming at B's saved rip.

The Verdict

Context switching is a complete register-state exchange through the PCB.

Its cost is microseconds — significant enough that the scheduler must be deliberate about when it happens, but small enough that human users never notice.

Every field of the PCB from L05 is either saved, restored, or unchanged during a context switch.

🔍 COMPREHENSIVE CRITIQUE: PROCESS CREATION STRATEGIES

Process Launch Across the Five Paradigms

Monolithic Process Launch

fork/exec are syscalls in the monolithic kernel. The kernel's copy_process() does the PCB clone; its do_execve() does the binary load. Two syscalls, two kernel functions, one unified pipeline.

Microkernel Process Launch

fork/exec are split across servers: process manager creates the PCB, file server reads the binary, memory server maps the address space. Each step is an IPC message. Slower, but each step is isolated and independently restartable.

Layered Process Launch

Strict layering — syscall layer → process layer → memory layer → file layer → driver layer. Each layer has a distinct interface and can be independently modified. POSIX's fork semantics could remain stable for 50 years because of this layering.

Modular Process Launch

The fork/exec implementation is in the kernel core, but the binary loading portion is modular — the ELF loader is a kernel module, alternative formats (scripts, Mach-O) are pluggable. binfmt_* modules on Linux execute arbitrary formats.

Hybrid Process Launch

fork/exec are syscalls (fast path), but the actual address space loading invokes the binfmt registry, which routes to pluggable format handlers. Additional LSM hooks on the fork/exec path for security. Fast and extensible simultaneously.

🏷️ SYSTEM LEXICON: MASTERING THE PROCESS LAUNCH VOCABULARY

Base fork/exec Terms

Term 01 · fork()

A system call that duplicates the calling process to create an isolated, matching child process container. The child receives a new PID but copies the parent's entire state — PCB fields, address space (via copy-on-write), and file descriptors. The only observable difference is the return value: 0 in the child, the child's PID in the parent.

(The perfect runner clone — identical at the moment of creation, diverging only by subsequent action.)

Term 02 · exec()

A system call that overrides the active process address space with a new executable binary program image. The old Text, Data, Heap, and Stack are discarded; new segments are loaded from disk; the program counter resets to the new binary's entry point. Success does not return — the caller is transformed into the new program.

(The new script overwrite — same body, completely new program.)

🏷️ SYSTEM LEXICON: MASTERING THE PROCESS LAUNCH VOCABULARY

Advanced Launch Terms

Term 03 · Context Switch

The physical hardware/software process of saving the active CPU register state into the outgoing process's PCB and restoring a different task's register context from its PCB; may also involve switching the page-table base register (CR3) and flushing the TLB if the two processes have separate address spaces.

(The referee's baton pass — pause one runner, save their position, resume another.)

Term 04 · Copy-on-Write (COW)

A memory optimization where parent and child share physical pages after fork(), both marked read-only; on the first write to any page by either process, the kernel's page fault handler duplicates that specific page so the writer gets a private copy. This makes fork() nearly free even for multi-gigabyte processes.

(The clone shares resources until they need to diverge — only then is a new copy made.)

Term 05 · PCB Save/Restore

The computational steps during a context switch that copy the CPU's current register state (including the program counter, stack pointer, general-purpose registers, and flags) into a process's PCB, and then load the incoming process's register values from its PCB back into the CPU before resuming execution.

(The bookmark set — capture every register, restore every register, resume exactly where the process stopped.)

💻 CODE DISSECTION: C FORK-EXEC LAUNCH PANEL

The Classic fork/exec Shell Launch

// Classic Unix fork-and-exec pattern — the "ls -l" launch
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/types.h>
#include <sys/wait.h>
#include <string.h>

int main() {
    pid_t rc = fork();  // 1. Clone the process

    if (rc < 0) {
        perror("fork");
        return 1;
    } else if (rc == 0) {
        // --- CHILD PROCESS BRANCH ---
        printf("[CHILD pid=%d ppid=%d] About to exec /bin/ls...\n",
               getpid(), getppid());

        // Build argument vector — must be NULL-terminated!
        char *args[] = { "/bin/ls", "-l", "/tmp", NULL };

        // 2. Transform into /bin/ls. This never returns on success.
        execv(args[0], args);

        // If exec returns, it failed — print error and exit
        perror("execv");
        _exit(127);   // _exit is async-signal-safe; exit() runs atexit handlers
    } else {
        // --- PARENT PROCESS BRANCH ---
        printf("[PARENT pid=%d] Forked child pid=%d. Waiting...\n",
               getpid(), rc);

        int status;
        pid_t finished = waitpid(rc, &status, 0);  // 3. Reap the child

        if (WIFEXITED(status)) {
            printf("[PARENT] Child %d exited with status %d\n",
                   finished, WEXITSTATUS(status));
        } else if (WIFSIGNALED(status)) {
            printf("[PARENT] Child %d was killed by signal %d\n",
                   finished, WTERMSIG(status));
        }
    }
    return 0;
}

Use code with caution.

💻 CODE DISSECTION: TRACING THE LAUNCH PIPELINE

Walking the fork-exec Trace

pid_t rc = fork()

The clone. Kernel duplicates the calling process. Both parent and child return from this syscall, but with different rc values. This is the only observable difference.

if (rc == 0)

The child branch. The child's first executable instruction after fork() is inside this if block — completely different from the parent's path.

execv("/bin/ls", args)

The transformation. The child's address space is destroyed and replaced with /bin/ls's. The child retains its PID, its PPID, its FD table — but gains entirely new Text/Data/Heap/Stack. The PC jumps to ls's entry point.

perror("execv"); _exit(127);

The failure path. Executes only if exec fails. Note _exit() instead of exit() — _exit() is a direct syscall that does not run the parent's atexit() handlers, avoiding side effects in the exec'd program's context.

waitpid(rc, &status, 0)

The reap. The parent waits for the child to terminate. Without it, the child becomes a zombie process (terminated, but its PCB is preserved until the parent reads its exit status).

WIFEXITED · WEXITSTATUS

Status decoding. Parent inspects the child's exit status. WIFSIGNALED checks for signal-induced termination (segfault, SIGKILL).

This 30-line pattern is the exact code every shell runs when you type ls -l /tmp.

🏆 RETROSPECTIVE: SYLLABUS DISSECTION SUMMARY

Grand Lecture Summary

01

fork() clones a process — the child is an exact copy of the parent's PCB, address space (via COW), and FDs. The only difference is the return value (0 in child, PID in parent). exec() transforms a process — destroys the current address space and loads a new binary, keeping the same PID and identity.

02

Copy-on-write makes fork() nearly free — parent and child share physical pages until one writes, at which point only that page is duplicated. This is why modern shells, servers, and containers can fork multi-gigabyte processes instantly.

03

A context switch is the save-restore cycle through the PCB — save registers into the outgoing process's PCB, load registers from the incoming process's PCB, resume at the new program counter. This is the fundamental operation that enables multitasking, and it is orchestrated by the scheduler (L07) we will study next.
