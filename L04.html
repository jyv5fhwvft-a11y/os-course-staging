The Core Objective

Chronologically sequence the four structural stages that occur between a user pressing a computer's physical power-on switch and the arrival of a user-space login prompt.

The Problem Hook: The CPU has no concept of "files." It can only execute machine instructions at a memory address. When you press the power button, RAM is empty and the disk is opaque — the CPU would have no idea where to begin even if it wanted to run Linux. So how does a running operating system come into existence from literally nothing? The answer is a four-stage relay: each stage has just enough capability to load the next, larger stage.

🛑 ENTRY BARRIERS: REQUIREMENT DIRECTIVES

Structural Prerequisites

01 · L01–L03 Foundation

The kernel architecture, the hardware privilege barrier, and the syscall interface. The boot process culminates in bringing all three online.

02 · Volatile vs Non-Volatile

The difference between storage that survives power-off (ROM, disks) and RAM that clears on power loss.

03 · Kernel as a File

A kernel binary is just a file on disk — an ELF executable containing machine code and data. It is not magical; it just needs to be loaded into memory before the CPU can execute it.

Teacher's Note: Every time you reboot, this entire four-stage relay runs. The OS is not persistent; it must be rebuilt from scratch at every boot. The boot process is the OS's own birth.

🎒 EVERYDAY SIMPLIFIED: THE BOOTSTRAP CHAIN

The Summary Metaphor

🔗 Tiny, Incapable Stages

UEFI can only verify hardware and hand off. The bootloader can only find and load the kernel. Each stage is limited.

🔗 Fully Capable Stages

The kernel builds everything. The init system launches user services. Each stage is more powerful than the last.

The chain is the answer to "how do you build something complex from nothing?" — you build it in stages, each slightly more capable than the last.

💻 SYSTEMS COHESION: THE HARDWARE VERIFICATION

Stage 1 — UEFI / BIOS

1. Power On

CPU resets to reset vector

→

2. Firmware

UEFI ROM code begins

→

3. POST

CPU, RAM, hardware checks

→

4. Handoff

Jump to bootloader

The Pipeline

1. Power applied: CPU resets. RIP = reset vector (0xFFFFFFF0 on x86-64).

2. Firmware executes: ROM code (UEFI on modern, BIOS on legacy) begins.

3. POST: Verifies CPU caches, RAM size, essential devices.

4. Hardware enumeration: UEFI builds ACPI tables describing all devices.

5. Boot device selection: Reads EFI System Partition, finds bootloader.

6. Jump to bootloader: Loads \EFI\BOOT\BOOTX64.EFI into memory.

The Verdict

The smallest stage, but performs critical functions: hardware verification, ACPI table generation, and boot device selection.

Runs at: highest CPU privilege level (Ring -2 on Intel) before the OS takes control.

Time: 1–5 seconds on modern systems.

💻 SYSTEMS COHESION: THE KERNEL LOADER

Stage 2 — The Bootloader

The Bootloader Pipeline (GRUB)

1. Init: UEFI-loaded bootloader initializes its environment.

2. Config: Reads /boot/grub/grub.cfg — lists boot entries.

3. Menu: Shows boot menu (user can select or edit).

4. Kernel load: Reads vmlinuz, decompresses, places at load address.

5. Initrd load: Loads initial RAM disk for early boot.

6. State setup: RDI → boot_params, RSI → initrd, CPU in protected mode.

7. Jump to kernel: Jumps to startup_64 entry point.

The Verdict

The middleman between firmware and kernel.

It knows how to read filesystems, load executable images, and pass command-line arguments — but it does not know how to run an OS.

Time: 0.1–1 second (dominated by disk I/O speed).

Examples: GRUB, systemd-boot, LILO, rEFInd.

💻 SYSTEMS COHESION: THE ENVIRONMENT CONSTRUCTION

Stage 3 — Kernel Initialization

The Initialization Pipeline

1. Entry: Kernel starts at startup_64.

2. Early setup: Decompression, initial page tables, GDT/IDT setup.

3. Hardware discovery: Parse ACPI tables (from UEFI).

4. Arch init: Bring up secondary CPUs, initialize MMU and TLB.

5. Subsystem init: Scheduler, memory manager, drivers, filesystems, security.

6. Initramfs unpack: Unpack initial RAM disk into memory.

7. Root mount: Mount real root filesystem, pivot_root.

8. Launch init: Start /sbin/init or systemd as PID 1.

The Verdict

The largest stage — it builds the entire operating environment from scratch.

Every subsystem from Modules 2–7 is initialized here: scheduler, memory manager, filesystems, drivers, security.

Time: 1–3 seconds (driver initialization dominates).

Where the OS actually begins to exist.

💻 SYSTEMS COHESION: THE USER-SPACE ORCHESTRATOR

Stage 4 — The Init System (PID 1)

The Init Pipeline (systemd)

1. Launch: Kernel launches /usr/lib/systemd/systemd as PID 1.

2. Mount: Mount rest of filesystems (/home, /var, swap).

3. Target processing: basic.target → multi-user.target → graphical.target.

4. Service startup: journald, udevd, NetworkManager, dbus, sshd, cron, and more.

5. Login handoff: Launch display manager (gdm, lightdm) or getty.

6. Session start: User authenticates, shell or desktop launches.

The Verdict

The first user-space process — the ancestor of every other process.

Transitions the system from "kernel running with no user software" to "fully operational multi-user environment."

Time: 2–10 seconds (parallel service startup).

Examples: systemd, OpenRC, runit, SysVinit.

💻 SYSTEMS COHESION: THE FOUR-STAGE SYNTHESIS

The Complete Boot Timeline

Stage 1 · UEFI

Time: 1–5s

Hardware verification, ACPI tables, boot device selection.

Stage 2 · Bootloader

Time: 0.1–1s

Kernel load, initramfs load, state setup, jump to kernel.

Stage 3 · Kernel

Time: 1–3s

Subsystem init, driver setup, root mount, init launch.

Stage 4 · Init

Time: 2–10s

Service startup, target activation, login prompt, session start.

Total: A modern laptop boots in ~5–15 seconds from power-on to login. A high-end NVMe desktop can reach login in 4 seconds. A traditional spinning-disk workstation might take 30–60 seconds.

🔗 SYSTEM PIPELINE: FEEDS INTO ALL SEVEN MODULES

Core System Cohesion — Feeds Into Everything

Module 2 (Process)

Kernel initializes scheduler, run queue, process table. PID 1 (systemd) is the ancestor of every process.

Module 3 (Memory)

Kernel initializes page allocator, virtual memory manager, page tables — the entire memory infrastructure.

Module 5 (Filesystem)

Kernel initializes VFS and registers filesystem drivers. Then mounts root from initramfs, systemd mounts everything else.

Module 6 (I/O)

Kernel initializes device drivers during Stage 3. UEFI enabled basic hardware; kernel drivers extend and take over.

Module 7 (Security)

Kernel initializes LSM hooks, capabilities, namespaces. UEFI Secure Boot validates bootloader signature.

The Verdict

L04 is the assembly of everything we studied — the proof that the OS is a buildable system from scratch.

🔍 COMPREHENSIVE CRITIQUE: KERNEL BOOT STRATEGIES

Boot Strategies Across the Five Paradigms

Monolithic Boot

Kernel initializes every subsystem at boot. Driver init runs serially. Boot time dominated by drivers. Some drivers can be deferred as modules, but core subsystems must be ready before user-space.

Microkernel Boot

Kernel is tiny (~10k lines in seL4), so boot is very fast — under 1s. But user-space servers must all start before the system is usable. Boot is a cooperative process — each server must start in the correct order with IPC channels established.

Layered Boot

Each layer initialized in strict order: layer 0 (hardware), then layer 1 (drivers), then layer 2 (scheduling), and so on. Easier to verify (each layer tested independently) but slower (no parallelism).

Modular Boot

Base kernel inits core subsystems in parallel using multiple cores, then driver modules load on demand. Some modules preloaded, most load when their hardware is detected. How Linux achieves fast boot despite supporting millions of devices.

Hybrid Boot

Kernel inits core subsystems in parallel, pre-launches a user-space initramfs containing essential tools, mounts real root, discards initramfs, continues from real root. Modern Linux boot is functionally hybrid.

🏷️ SYSTEM LEXICON: MASTERING THE BOOT VOCABULARY

Base Boot Terms

Term 01 · UEFI (Unified Extensible Firmware Interface)

Modern motherboard firmware that initializes hardware, runs the Power-On Self-Test, enumerates attached devices, and bootstraps the OS bootloader by locating an EFI System Partition and executing the configured .efi boot loader file. Replaces legacy BIOS. Runs at the highest CPU privilege level before the OS takes control.

(The security guard who checks the venue is ready and opens the main gate.)

Term 02 · Bootloader

A lightweight intermediate utility (e.g., GRUB, LILO, systemd-boot) responsible for locating, loading, and executing the operating system kernel binary from storage; also loads an initial RAM disk (initramfs) if needed. It is the bridge between firmware and the kernel — the second stage in the boot chain.

(The locker room manager who finds the champion and points them to the track.)

🏷️ SYSTEM LEXICON: MASTERING THE BOOT VOCABULARY

Advanced Boot Terms

Term 03 · systemd / init

The primordial user-space process (PID 1) responsible for spawning and managing all system daemons and shell interfaces; it is the ancestor of every process on the system, initialized by the kernel as the very first Ring 3 execution. On modern Linux, systemd performs parallel service startup, dependency resolution, and target activation.

(The stadium gatekeeper who opens all doors and starts all services.)

Term 04 · POST (Power-On Self-Test)

The initial hardware diagnostic routine run by motherboard firmware (UEFI/BIOS) immediately after power is applied, to verify system readiness — CPU function, RAM integrity, keyboard/display presence, and basic device enumeration. Failure at this stage typically means the system will not boot at all.

(The security guard's initial walkthrough to verify the venue is structurally sound.)

Term 05 · initramfs

A small filesystem image loaded into memory (by the bootloader) that provides a minimal user-space environment during kernel initialization; contains just enough drivers and tools to find, mount, and pivot to the real root filesystem. Once the real root is mounted, the initramfs is discarded from memory.

(The temporary construction office used to build the actual stadium before the main grand opening.)

💻 CODE DISSECTION: C BOOT TELEMETRY PANEL

Inspecting the Boot Process from User Space

// Inspecting the results of the boot process from user space
#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <sys/utsname.h>

// Helper: read a line from a virtual file, strip newline
int read_first_line(const char* path, char* buffer, size_t bufsize) {
    FILE* f = fopen(path, "r");
    if (!f) { buffer[0] = '\0'; return -1; }
    if (!fgets(buffer, bufsize, f)) { fclose(f); buffer[0] = '\0'; return -1; }
    fclose(f);
    buffer[strcspn(buffer, "\n")] = '\0';
    return 0;
}

int main() {
    printf("=== Boot Process Telemetry ===\n\n");

    // --- What the kernel learned from UEFI/BIOS ---
    char bios_version[128];
    if (read_first_line("/sys/class/dmi/id/bios_version", bios_version, sizeof(bios_version)) == 0) {
        printf("[STAGE 1 — UEFI/BIOS Handoff]\n");
        printf("  BIOS version:  %s\n", bios_version);
    }

    char bios_vendor[128];
    if (read_first_line("/sys/class/dmi/id/bios_vendor", bios_vendor, sizeof(bios_vendor)) == 0) {
        printf("  BIOS vendor:   %s\n", bios_vendor);
    }

    // --- What the bootloader loaded ---
    struct utsname uts;
    if (uname(&uts) == 0) {
        printf("\n[STAGE 2 & 3 — Bootloader + Kernel Init]\n");
        printf("  Kernel:        %s\n", uts.sysname);
        printf("  Release:       %s\n", uts.release);
        printf("  Arch:          %s\n", uts.machine);
    }

    char cmdline[512];
    if (read_first_line("/proc/cmdline", cmdline, sizeof(cmdline)) == 0) {
        printf("  Kernel cmdline: %s\n", cmdline);
    }

    char uptime[64];
    if (read_first_line("/proc/uptime", uptime, sizeof(uptime)) == 0) {
        printf("  Uptime:        %s seconds since boot\n", uptime);
    }

    // --- What the init system has launched ---
    printf("\n[STAGE 4 — Init System]\n");
    printf("  PID 1 (init):  ");
    fflush(stdout);
    system("ps -p 1 -o comm= 2>/dev/null");

    printf("  Total procs:   ");
    fflush(stdout);
    system("ps -e --no-headers | wc -l");

    // --- Kernel boot log excerpt ---
    printf("\n[Boot Log Excerpt from dmesg]\n");
    system("dmesg 2>/dev/null | grep -iE 'Linux version|Command line|ACPI:' | head -5");

    return 0;
}

Use code with caution.

💻 CODE DISSECTION: TRACING BOOT ARTIFACTS

Walking the Boot Telemetry Trace

/sys/class/dmi/id/bios_version

Stage 1 evidence. UEFI/BIOS populated the DMI tables with hardware identity. The BIOS version string is a direct artifact of the firmware's initialization.

/sys/class/dmi/id/bios_vendor

Stage 1 evidence. Reports which firmware vendor ran at power-on (AMI, Award, Insyde, Apple, etc.).

uname(&uts)

Stage 2 and Stage 3 evidence. The kernel's version is the exact vmlinuz binary the bootloader loaded. Each minor kernel version corresponds to a specific boot entry.

/proc/cmdline

Stage 2 evidence. The kernel command line is a bootloader-supplied string. On Ubuntu: BOOT_IMAGE=/boot/vmlinuz-6.x.x root=UUID=... ro quiet splash — literally what GRUB passed at startup.

/proc/uptime

Stage 3 evidence. The kernel's monotonic clock began at t=0 during Stage 3. The current uptime counts seconds since that moment.

ps -p 1 & ps -e

Stage 4 evidence. PID 1 is the init system. Every process on the system is a descendant of PID 1. The count measures how many services init has launched.

🏆 RETROSPECTIVE: SYLLABUS DISSECTION SUMMARY

Grand Lecture Summary

01

The boot process is a four-stage relay — UEFI/BIOS verifies hardware (Stage 1), the bootloader locates and loads the kernel (Stage 2), the kernel initializes all subsystems (Stage 3), and the init system launches user-space services (Stage 4). Each stage has just enough capability to make the next stage possible.

02

Stage 3 (kernel initialization) is the largest stage — it constructs every subsystem we will study in Modules 2–7: the scheduler, memory manager, filesystem, driver framework, and security layer. The boot process is literally the OS being built in real time.

03

The four stages are not arbitrary — they are derived from the hardware constraint that the CPU cannot load an OS from disk directly. The chain of capability is the answer to "how do you build a complex system from nothing?" — build it in stages, each slightly more capable than the last.
