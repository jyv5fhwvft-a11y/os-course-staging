The Core Objective

Apply an access control matrix and distinguish an Access Control List (ACL) from a capability token.

The Problem Hook: A modern operating system contains thousands of users and millions of resource objects — files, devices, sockets, shared memory segments. The full Access Control Matrix mapping every user to every object would require trillions of entries. But almost all of those entries are empty — User Alice has no permission to touch User Bob's photo, User Carol's database, or most of the system's memory. How do we store and enforce this matrix without physically allocating quadrillions of bits?

🎒 EVERYDAY SIMPLIFIED: THE OFFICE DIRECTORY BOARD

The Access Control Matrix Metaphor

🏢📋✅
The Narrative

Imagine a giant directory board at an office building's entrance. The rows list every employee's name; the columns list every room's number. Each cell has a checkmark (allowed) or an X (denied). To decide whether Alice may enter the server room, the security guard checks row "Alice," column "Server Room." This is the Access Control Matrix — the complete theoretical model of who can access what.

Execution Path

Every security policy is, mathematically, an entry in this matrix. The matrix is the specification; the entire challenge of access control is how to store and query it efficiently.

Micro-Accessibility Context

The matrix itself is the abstract concept — the next two slides show how it is actually implemented in practice.

🎒 EVERYDAY SIMPLIFIED: THE HOTEL ROOM DOOR REGISTRY

The ACL Metaphor

🚪📋👥
The Narrative

Instead of a giant directory at the entrance, each hotel room simply has a registry card attached to its own door. The card lists every person allowed into this specific room. When someone walks up and swipes their keycard, the door checks the registry. If your name is on the card, you enter. If not, the door stays locked.

Execution Path

An Access Control List (ACL) stores permissions on the resource itself. It is a column of the access matrix — every row for one resource, stored locally at that resource.

Micro-Accessibility Context

ACLs are resource-centric: the check happens at the resource, and the resource knows its allowed list.

🎒 EVERYDAY SIMPLIFIED: THE PHYSICAL KEYCARD

The Capability Metaphor

🎫🔑🚪
The Narrative

Instead of every door keeping a registry, the employee carries a keycard that lists every room they may enter. Door 204 does not know who Alice is — it just knows that the card presented has been cryptographically signed by the hotel manager as "authorized for 204." Doors do not check registries; they check tokens.

Execution Path

A Capability stores permissions with the user or process. It is a row of the access matrix — every column for one subject, stored with that subject.

Micro-Accessibility Context

Capabilities are subject-centric: the check happens when the subject presents the token, and the resource trusts the token's authority.

🎒 EVERYDAY SIMPLIFIED: THE TRAFFIC LIGHT TRIAD

The Permission Bit Metaphor

🚦📁🔢
The Narrative

Unix took the theoretically-infinite access matrix and compressed it into a beautifully simple nine-bit vector: three permissions (read, write, execute) times three classes (owner, group, others). This is not the full matrix — but it captures 99% of real-world use cases in nine bits per file.

Execution Path

rwxr-xr-- decodes to "owner read/write/execute, group read/execute, others read only." The kernel checks the current process's uid/gid against the file's owner/group to pick which triplet to enforce.

Micro-Accessibility Context

This is Unix's pragmatic concession: rather than the full access matrix, it stores a small, fast, sufficient approximation.

🎒 EVERYDAY SIMPLIFIED: THE ACCESS CONTROL DUALITY SUITE

The Summary Metaphor

🚪 Resource-Side (ACL)

Policy is stored at the resource. The resource knows who may access it. Column-oriented access matrix.

🎫 Subject-Side (Capability)

Policy is stored with the subject. The subject presents a token proving authorization. Row-oriented access matrix.

Access control has exactly two implementation strategies. Both are valid. Both enforce the same abstract matrix. The choice depends on which side scales better for the use case — and real systems often blend both.

💻 SYSTEMS COHESION: THE FORMAL PERMISSION GRID

The Access Control Matrix Foundation

Subject file1 file2 /dev/sda Shared Memory
Alice R, W R — —
Bob R R, W R —
Charlie — R — R, W, X
System Daemon — R R, W —

The Matrix Structure

Rows (Subjects): Every user, process, or protection domain.

Columns (Objects): Every protected resource. Files, directories, devices, sockets, shared memory.

Cells: The permission set the subject has on that object.

The Verdict

Every permission check in every OS is, mathematically, a lookup in this matrix.

The design question is how to store and query it.

💻 SYSTEMS COHESION: WHY THE MATRIX CANNOT FIT IN MEMORY

The Sparsity Problem

📊 The Full Matrix (Impossible)

10,000 users × 10,000,000 files = 10¹¹ (100 billion) cells.

At 1 byte per cell: 100 GB just for permissions.

Almost all cells are empty.

vs

✅ Compact Storage

ACL (column-oriented): Store only the non-empty cells for each object.

Capability (row-oriented): Store only the non-empty cells for each subject.

The same matrix, stored sparsely.

The Verdict: The entire history of access control is a design choice between two compact representations, each optimized for a different query pattern. There is no way around the sparsity — the matrix must be compressed.
💻 SYSTEMS COHESION: THE RESOURCE-SIDE ENFORCEMENT

Access Control List Internals

/etc/passwd ACL (conceptual)
user:alice:rw-
user:bob:r--
group:devs:rwx
other:r--

The Lookup Algorithm

When a process requests access, the kernel walks the ACL list looking for the first matching entry — user, then group memberships, then "other."

The most specific match wins.

The Unix Permission Bits

The classic rwxr-xr-- in every inode is just a compressed ACL with exactly three entries: owner, group, and others.

POSIX ACLs extend this with per-user and per-group entries stored in extended inodes.

💻 SYSTEMS COHESION: THE SUBJECT-SIDE ENFORCEMENT

Capability Token Internals

struct capability {
  object_id: 0x0042A1; // Unforgeable resource ID
  permissions: R | W | X; // Rights granted
  signature: 0xC0FFEE; // Kernel-signed proof
};

The Verification Algorithm

When the process presents a capability, the resource trusts it because the kernel signed it. The resource does not consult any registry — it validates the signature.

The Capability Invariants

Unforgeable: A user process cannot construct a new capability.

Transferable: Capabilities can optionally be passed between cooperating processes.

Revocable with difficulty: Removing a capability from a running process is notoriously hard.

💻 SYSTEMS COHESION: REAL-WORLD ACL AND CAPABILITY HYBRID

Unix Permission Bits and setcap

Owner

rwx

The UID that owns the file. Full control.

Group

r-x

Members of the file's GID. Read and execute.

Others

r--

Everyone else. Read only.

File Permissions (ACL)

chmod, chown — every file's rwxr-xr-- bits are a compressed ACL. POSIX ACLs (setfacl) extend this for granular per-user entries.

Linux Capabilities (Capability)

The kernel can grant fine-grained privileges to specific binaries. Instead of "root can do anything," setcap cap_net_bind_service+ep /usr/bin/myapp grants only "bind to low ports" to one binary.

Modern Linux uses both models simultaneously — ACL for files, capabilities for privileged operations.

🔗 SYSTEM PIPELINE: RELIES ON HARDWARE ENFORCEMENT

Core System Cohesion — Relies On L02

L02's Barrier

Access control is only enforceable because the check runs at a higher privilege level than the requester. In Ring 3, an app cannot rewrite its own ACL entry or capability token — the kernel enforces the matrix from Ring 0.

The Architectural Bond

If the dual-mode barrier were absent, an app could simply rewrite the permission bits it needed and bypass all security. The hardware barrier is the security foundation; the software ACL is the policy running on it.

Feeds Into L23

ACLs require verified identity — you cannot check "who is asking" against "who is allowed" without proven identity. This is why L23 (authentication) follows immediately.

Feeds Into L27

Containers (L27) wrap every process's capabilities into a namespace-scoped security domain — the ultimate generalization of the ACL model.

🔗 SYSTEM PIPELINE: FEEDS INTO AUTH AND ISOLATION

Core System Cohesion — Feeds Into L23 & L27

L23 (Authentication)

ACLs are meaningless without identity verification. Every permission check compares "who is asking" against "who is allowed" — but the "who" must be provable. Passwords, biometrics, hardware tokens.

L24 (Exploits)

Buffer overflow exploits (L24) attempt to bypass ACLs by hijacking execution inside Ring 0. Every mitigation (ASLR, canaries, NX) is a defense against ACL bypass.

L25 (Encryption)

Encryption protects data in transit — but the resource that decrypts it must still enforce its ACLs. Encryption is the confidentiality layer; ACLs are the authorization layer.

L27 (Isolation)

Containers extend the ACL model to entire process groups via namespaces and cgroups — the ultimate generalized access control framework.

🔍 COMPREHENSIVE CRITIQUE: ACCESS CONTROL STRATEGIES

Access Control Across the Five Paradigms

Monolithic Access Control

SELinux and standard Unix permissions live entirely in Ring 0. Every open() syscall triggers a check against the file's ACL and, if SELinux is active, against a policy database. Centralized and fast, but policy changes require reloading from Ring 0.

Microkernel Access Control

Capability-based microkernels (seL4, EROS, Coyotos) use an all-capability model — no ACLs, only unforgeable tokens. Every IPC channel and memory region access requires holding the right capability. Provably secure, but unforgiving.

Layered Access Control

Strict tier separation — hardware sandboxing (Ring 0/Ring 3) → OS ACLs (kernel) → application-level access control (e.g., database GRANT). Each layer enforces the same policy from a different trust level.

Modular Access Control

Linux's actual model — the base ACL check is in the kernel, but LSM (Linux Security Modules) hooks let pluggable modules like SELinux, AppArmor, and Smack inject additional policy checks at each syscall point.

Hybrid Access Control

Standard Unix ACLs for common use, plus Linux capabilities for privilege reduction, plus SELinux for mandatory access control. Modern enterprise systems run all three simultaneously.

🏷️ SYSTEM LEXICON: MASTERING THE SECURITY VOCABULARY

Base Access Control Terms

Term 01 · Access Control Matrix

A conceptual grid mapping user or process protection domains (rows) against system resource objects (columns) to define structural read, write, and execute permissions; the mathematical specification that every access control mechanism — ACLs and capabilities alike — approximates. Enormous in theory (10¹¹ cells on a typical system) but overwhelmingly sparse in practice.

(The master office directory board listing who may enter which room.)

Term 02 · Access Control List (ACL)

A column-oriented optimization of the access control matrix where permissions are stored directly on the resource object; each resource maintains a list of {subject, permissions} entries, and lookups walk this list to determine whether a requester is allowed. The most common real-world implementation — every Unix file mode is a tiny compressed ACL.

(The laminated card clipped to the door listing who is allowed inside.)

🏷️ SYSTEM LEXICON: MASTERING THE SECURITY VOCABULARY

Advanced Access Control Terms

Term 03 · Capability

A row-oriented security optimization where an unforgeable kernel-issued token is held by a subject process and presented to protected resources to prove authorization; the resource trusts the token without consulting any registry, and the token cannot be forged or duplicated by user code. Provides stronger guarantees than ACLs at the cost of harder revocation.

(The employee's signed keycard listing which rooms they may enter.)

Term 04 · Protection Domain

The bounded execution environment profile that determines which operations a thread is permitted to perform across various system objects; typically defined by the process's uid, gid, supplementary groups, and its capability set. Every thread in a process shares the same protection domain unless explicitly changed.

(The employee's badge color — blue for engineering, red for security, gold for executives.)

Term 05 · Privilege Escalation

An attack in which a process or user obtains permissions beyond those granted by the access control policy; may be vertical (user → root) or horizontal (user A → user B). Often the target of exploits against misconfigured ACLs, leaked capabilities, or buffer overflows (L24).

(Sneaking into a room whose door card you were not given.)

💻 CODE DISSECTION: C ACL SIMULATOR

Implementing a Minimal ACL Check in C

// Simulating a minimal resource-side ACL check in C
// Compile: gcc -o acl acl.c && ./acl
#include <stdio.h>
#include <string.h>

#define MAX_ENTRIES 8

typedef enum { PERM_NONE = 0, PERM_READ = 1, PERM_WRITE = 2,
               PERM_EXEC = 4 } Permission;

typedef struct {
    char username[32];
    Permission perms;
} ACLEntry;

typedef struct {
    ACLEntry entries[MAX_ENTRIES];
    int count;
} ACL;

void acl_add(ACL* acl, const char* user, Permission perms) {
    if (acl->count < MAX_ENTRIES) {
        strncpy(acl->entries[acl->count].username, user, 31);
        acl->entries[acl->count].perms = perms;
        acl->count++;
    }
}

int acl_check(ACL* acl, const char* user, Permission requested) {
    for (int i = 0; i < acl->count; i++) {
        if (strcmp(acl->entries[i].username, user) == 0) {
            // Match found — check if requested permission is present
            return (acl->entries[i].perms & requested) == requested;
        }
    }
    return 0;  // User not in list — default deny
}

int main() {
    ACL file_acl = { .count = 0 };
    acl_add(&file_acl, "alice", PERM_READ | PERM_WRITE);
    acl_add(&file_acl, "bob",   PERM_READ);
    acl_add(&file_acl, "carol", PERM_READ | PERM_WRITE | PERM_EXEC);

    printf("ACL CHECK RESULTS:\n");
    printf("Alice read:  %s\n",
        acl_check(&file_acl, "alice", PERM_READ) ? "GRANTED" : "DENIED");
    printf("Alice write: %s\n",
        acl_check(&file_acl, "alice", PERM_WRITE) ? "GRANTED" : "DENIED");
    printf("Alice exec:  %s\n",
        acl_check(&file_acl, "alice", PERM_EXEC) ? "GRANTED" : "DENIED");
    printf("Bob   write: %s\n",
        acl_check(&file_acl, "bob", PERM_WRITE) ? "GRANTED" : "DENIED");
    printf("Eve   read:  %s\n",
        acl_check(&file_acl, "eve", PERM_READ) ? "GRANTED" : "DENIED");

    return 0;
}

Use code with caution.

💻 CODE DISSECTION: TRACING ACL VERIFICATION WEIGHTS

Walking the ACL Check Trace

acl_add(&file_acl, "alice", PERM_READ | PERM_WRITE)

Column-oriented write. Adds a specific subject-permission pair to the resource's ACL. We are modifying one column (this file) of the access matrix.

acl_check(&file_acl, "alice", PERM_READ)

Linear scan + bitmask check. Walks the ACL entries, finds Alice's, checks her PERM_READ bit. GRANTED — bit is set. This is a resource-side check.

acl_check(&file_acl, "alice", PERM_EXEC)

Same scan, bit not set. Alice's permissions lack PERM_EXEC. DENIED.

acl_check(&file_acl, "eve", PERM_READ)

Not in list → default deny. eve is not in the list; the function falls through to return 0. The default-deny principle is the correct security posture: no ACL entry = no access.

perms & requested

The critical permission check. The & operator tests whether every requested bit is present. This is why permissions are bitmasks — it makes the check a single instruction.

The Verdict

ACLs are astonishingly simple — a linear list of {user, bitmask} entries with a default-deny rule. This is what protects every /dev device, every /etc config file, and every /home directory on a Unix system.
