The Core Objective

Calculate Effective Access Time (EAT) equations using hit-rate variables, hardware cache check latencies, and physical RAM access latency boundaries.

The Problem Hook: L11 taught us that paging is beautiful — but expensive. Every memory access now requires two trips to physical RAM: one to look up the page table entry, and one to read the actual data. If every load and store doubled in cost, modern CPUs would be unusable. But they are not — a 3 GHz processor executes billions of instructions per second without breaking a sweat. What invisible trick hides the paging tax so completely?

🎒 EVERYDAY SIMPLIFIED: THE STICKY NOTE ON THE MONITOR

The TLB Metaphor

📝📞📖
The Narrative

Imagine you work as a researcher who constantly needs to look up phone numbers in a massive 1,000-page directory book kept across the room. Every time you want to make a call, walking across the room to check the book slows you down heavily. To solve this, you stick a small piece of paper right next to your telephone — the sticky note. When you look up a number for the first time, you write it on the sticky note. The next time you call that exact same person, you don't walk across the room; you glance at the sticky note instantly.

Execution Path

The sticky note is the TLB. The phonebook is the page table. A "hit" means the number is on your note; a "miss" means you walk to the book.

Micro-Accessibility Context

You only walk to the phonebook when the note is missing the name — the TLB's entire value comes from the locality of real workloads.

🎒 EVERYDAY SIMPLIFIED: THE HOLOGRAPHIC LOOKUP

The Associative Lookup Metaphor

⚡🔀🔍
The Narrative

Imagine a switchboard operator who can look at 64 different filing cards simultaneously — not one after another, but all at the same instant. The operator compares your incoming name against every card on the board in a single flash. This is content-addressable memory (CAM) — a hardware trick that makes the TLB far faster than an ordinary memory lookup.

Execution Path

The TLB is built with associative memory. It checks all entries in parallel — no linear scan, no index arithmetic. Hardware does this in a single clock cycle.

Micro-Accessibility Context

This parallel-search hardware is what makes the TLB fast enough to be on the critical path of every memory access.

🎒 EVERYDAY SIMPLIFIED: THE DESK DRAWER

The Locality Metaphor

📁🗄️🏃
The Narrative

You reference the same client files repeatedly during a workday. Keeping those specific folders right on top of your desk saves you from walking down the hall to the filing room archive cabinet for every single document. Because your work touches only a few files repeatedly, the desk-drawer version handles 95%+ of your requests.

Execution Path

Programs exhibit spatial and temporal locality — they touch the same pages repeatedly. Only a small working set of translations matters at any given moment. The TLB is sized (64–2048 entries) to hold that working set.

Micro-Accessibility Context

Without locality, no cache of any kind would work — not the TLB, not L1/L2/L3, not the page cache. Locality is the most important property in computer performance.

🎒 EVERYDAY SIMPLIFIED: THE SHUFFLED CACHE

The Context Switch Flush Metaphor

🔄❌🔒
The Narrative

When you switch to a different job, the sticky note on your desk is suddenly wrong — it was for the previous task's files. So on every context switch, you wipe the note clean. This is what old CPUs did with the TLB on every process switch — an expensive flush that cost microseconds.

Execution Path

Modern CPUs add an ASID (Address Space Identifier) tag to each TLB entry. Instead of flushing the TLB, the CPU simply tags entries with the current process's ASID and skips entries from other processes. No flush required.

Micro-Accessibility Context

ASIDs are a small feature with enormous performance impact — they eliminate most TLB flushes on modern multitasking systems.

🎒 EVERYDAY SIMPLIFIED: THE TLB ACCELERATION SUITE

The Summary Metaphor

✅ Lightning-Fast Hits

Most translations (95–99%) are cached. A single-cycle associative lookup. The page table walk is skipped entirely.

❌ Rare Slow Misses

Occasional translations miss the cache and fall back to the page table walk. The 2× penalty now hits only ~1–5% of accesses.

The TLB transforms a uniformly painful 2× memory tax into a rare edge case — effectively restoring single-access memory performance for 95%+ of operations. This is why paging is fast enough for production.

💻 SYSTEMS COHESION: THE ASSOCIATIVE HARDWARE CACHE

TLB Architecture & CAM Structure

The TLB Structure

The Translation Lookaside Buffer (TLB) is a specialized, ultra-fast hardware cache located directly inside the CPU Memory Management Unit (MMU).

Size: 64 to 2,048 entries typically (L1 TLB). L2 TLB may have 2,000–4,000 entries.

Technology: Content-Addressable Memory (CAM) — checks all entries in parallel.

Latency: 1–2 clock cycles for a hit. Compared to ~100 cycles for a page table walk.

The Vector Pairing

Tag Field: Stores virtual page numbers (plus ASID on modern CPUs).

Data Field: Stores corresponding physical frame numbers + protection permission bits (R/W/X) + dirty bit + valid bit.

The full entry: {ASID, VPN} → {PFN, permissions, flags}

Every translation the CPU performs is a lookup against this table — either hits (fast) or misses (slow).

💻 SYSTEMS COHESION: THE LOOKUP DECISION TREE

The TLB Hit vs. Miss Pipeline

1

CPU issues virtual address. The MMU intercepts it before any memory access happens.

2

TLB lookup (parallel CAM). The MMU compares the virtual page number (and ASID) against every TLB entry simultaneously.

3

Decision: HIT or MISS. If a valid matching entry is found → TLB hit. Otherwise → TLB miss.

✅ TLB Hit Path (95–99% of accesses)

Cost: 1–2 cycles for the TLB lookup.

Then: Physical address is computed directly, one memory access to fetch data.

Total: ~1 memory access + small TLB overhead. Almost as fast as base-and-bound.

❌ TLB Miss Path (1–5% of accesses)

Cost: 1 TLB lookup (fails) + 1 page table walk (multiple memory accesses for multi-level tables) + 1 memory access for data.

Then: The kernel's page walker or hardware walks the page table, finds the frame, installs the entry in the TLB, and retries.

Total: ~2× memory access cost. But it happens rarely.

💻 SYSTEMS COHESION: THE MATHEMATICAL DERIVATION

Effective Access Time (EAT) Formula

The EAT Equation

EAT is the weighted average memory access time, factoring in TLB hit rate and RAM access latency:

EAT = h × (TLB_lookup + RAM_access) + (1 − h) × (TLB_lookup + 2 × RAM_access)

Variable Breakdown:

· h = TLB hit rate (percentage expressed as decimal, e.g., 0.95)

· TLB_lookup = TLB search time (typically 1–10 ns)

· RAM_access = physical memory access time (typically 100 ns)

· 1 − h = miss rate

Hit Case

On a hit, the TLB provides the physical frame number directly. One memory access fetches the data. Total cost: TLB_lookup + RAM_access.

Miss Case

On a miss, the CPU must walk the page table (first memory access), then fetch the data (second memory access). Total cost: TLB_lookup + 2 × RAM_access.

💻 SYSTEMS COHESION: THE FULL WORKED CALCULATION

Quantitative EAT Calculation Example

The Setup

TLB search = 20 ns · RAM access = 100 ns · Hit rate h = 80% (0.80)

Step-by-Step Solution

Step 1 — Hit path contribution:

0.80 × (20 + 100) = 0.80 × 120 = 96 ns

Step 2 — Miss path contribution:

0.20 × (20 + 2×100) = 0.20 × 220 = 44 ns

Step 3 — Sum:

EAT = 96 + 44 = 140 ns

❌ Without TLB

Every access pays the full 2× penalty: 2 × 100 = 200 ns.

✅ With TLB (80% hit)

Average access time = 140 ns — a 30% reduction.

At 99% hit rate → 0.99×120 + 0.01×220 = 121 ns — nearly restoring single-access speed.

Why Modern CPUs Hit 99%+

Locality: Real workloads touch small working sets — loops, hot functions, adjacent data. These fit in the TLB.

Multi-level TLB: L1 TLB (64 entries, 1 cycle) → L2 TLB (2000 entries, 6 cycles) → L3 TLB (part of L3 cache).

Huge pages: 2 MB or 1 GB pages drastically reduce TLB pressure — one entry covers 512× more memory than a 4 KB page.

Modern workloads rarely fall below 95% TLB hit rate.

🔗 SYSTEM PIPELINE: RELIES ON PAGING MECHANICS

Core System Cohesion — Relies On L11

L11's Cost Problem

Every virtual address access requires a page table lookup. Without caching, this doubles every memory operation — untenable for CPU-intensive workloads.

L12's Solution

The TLB caches recent page table entries. Instead of walking the table every time, the MMU checks the TLB first — and 95%+ of the time, it finds the answer there.

The Architectural Bond

The TLB exists because paging exists. It is not a general caching mechanism — it specifically caches the translations that paging produces. Without paging, no TLB.

Feeds Into L13

TLB miss handling interacts with page fault handling (L13): a TLB miss may trigger a page table walk, which may discover an absent page, which triggers a page fault. The two layers must cooperate.

🔗 SYSTEM PIPELINE: FEEDS INTO VIRTUAL MEMORY

Core System Cohesion — Feeds Into L13

L13 (Demand Paging)

When the TLB misses and the page table walk finds valid = 0, a page fault occurs. The kernel must fetch the page from disk (or swap), install the page table entry, and — crucially — invalidate the stale TLB entry if one exists.

The TLB Shootdown

When a page is modified or unmapped on one CPU, other CPUs may have stale TLB entries. The kernel must send IPIs (inter-processor interrupts) to flush them — a "TLB shootdown." This is a costly operation and a key optimization target in modern kernels.

ASID Tagging

Modern CPUs tag TLB entries with an ASID (Address Space Identifier). This lets the TLB hold entries from multiple processes simultaneously — no flush needed on every context switch (L06).

The Module 3 Arc Complete

L10 (base-bound) → L11 (paging) → L12 (TLB) → L13 (demand paging). The TLB makes paging fast; demand paging makes paging expand to disk. Together they deliver the complete illusion of infinite memory.

🔍 COMPREHENSIVE CRITIQUE: TLB STRATEGIES

TLB Management Across the Five Paradigms

Monolithic TLB Management

TLB invalidation and hardware register flushes execute directly within privileged Ring 0 kernel supervisor space. The kernel directly executes invlpg instructions to flush TLB entries and manages the CR3 register on every context switch.

Microkernel TLB Management

TLB management primitives run in Ring 0 hardware drivers, while virtual memory mapping managers operate in user space. The kernel provides only the minimal TLB manipulation syscalls; the policy (when to shoot down, which pages to map) is decided by user-space services.

Layered TLB Management

Enforces strict hierarchical cache validation checks down vertical memory abstraction tiers. Layer N's TLB entries must be consistent with Layer N-1's page tables — the hardware and kernel co-verify the layering.

Modular TLB Management

Maintains core MMU cache flushing loops in Ring 0 while allowing specialized architecture performance modules to load dynamically. Different TLB management strategies for different hardware (Intel vs AMD vs ARM) live in swappable modules.

Hybrid TLB Management

Critical hardware TLB shootdowns execute inside Ring 0 supervisor space while container virtualization daemons (L27) coordinate address spaces. The kernel handles low-level shootdowns; userspace orchestration controls which VMs/containers trigger them.

🏷️ SYSTEM LEXICON: MASTERING THE TLB VOCABULARY

Base TLB Terms

Term 01 · TLB (Translation Lookaside Buffer)

A specialized, ultra-fast associative hardware cache inside the CPU's MMU used to accelerate virtual-to-physical address translations. Holds recently-used (VPN → PFN) mappings in Content-Addressable Memory, allowing parallel lookup of the page number in a single cycle. Typical size: 64–2048 entries.

(The speed-dial memory storing frequent phone numbers instantly.)

Term 02 · TLB Hit Rate

The statistical probability percentage indicating that a requested virtual address translation was successfully found inside the TLB cache. Modern CPUs achieve 95–99% hit rates on typical workloads due to spatial/temporal locality. Hit rate is the single most important factor in overall memory performance.

(The percentage of times your speed-dial button successfully connects without opening the phonebook.)

🏷️ SYSTEM LEXICON: MASTERING THE TLB VOCABULARY

Advanced TLB Terms

Term 03 · Effective Access Time (EAT)

The calculated average time required to access memory, factoring in TLB lookup speeds, cache hit rates, and RAM access penalties. Computed as a weighted average: EAT = h × (TLB + RAM) + (1−h) × (TLB + 2×RAM). The primary metric for evaluating paging system performance.

(The true average time spent looking up and retrieving a file from storage.)

Term 04 · ASID (Address Space Identifier)

A hardware tag appended to TLB entries identifying which specific process owns that translation mapping. Allows the TLB to hold entries from multiple processes simultaneously, eliminating the need for a full TLB flush on every context switch. Typical ASID width: 8–16 bits (256–65536 address spaces).

(Color-coded name tags preventing workers from using another department's folder.)

Term 05 · TLB Shootdown

An inter-processor interrupt signal used in multi-core systems to force other CPU cores to invalidate stale TLB cache entries. Triggered when a page is unmapped, its permissions are changed, or a process is terminated. TLB shootdowns are expensive (each CPU must handle an IPI) and are a key optimization target in kernel design.

(Broadcasting an emergency radio alert telling all team stations to update their contact lists.)

💻 CODE DISSECTION: C EAT LATENCY SIMULATOR

Simulating EAT Under Varying Hit Rates

// Calculating Effective Access Time (EAT) under varying TLB hit rates in C
// Run: gcc -o eat eat.c && ./eat
#include <stdio.h>

void calculate_eat(double hit_rate, double tlb_ns, double ram_ns) {
    // EAT Formula: h * (TLB + RAM) + (1 - h) * (TLB + 2 * RAM)
    double eat = (hit_rate * (tlb_ns + ram_ns))
               + ((1.0 - hit_rate) * (tlb_ns + (2.0 * ram_ns)));

    printf("Hit Rate: %5.1f%% | TLB: %.1fns | RAM: %.1fns -> EAT: %.2f ns\n",
           hit_rate * 100.0, tlb_ns, ram_ns, eat);
}

void calculate_speedup(double hit_rate, double tlb_ns, double ram_ns) {
    double eat = (hit_rate * (tlb_ns + ram_ns))
               + ((1.0 - hit_rate) * (tlb_ns + (2.0 * ram_ns)));
    double without_tlb = 2.0 * ram_ns;  // Always 2 trips
    double speedup = without_tlb / eat;

    printf("  Without TLB: %.2f ns | Speedup: %.2fx\n",
           without_tlb, speedup);
}

int main() {
    double tlb_latency = 20.0;   // 20 ns TLB lookup
    double ram_latency = 100.0;  // 100 ns RAM access

    printf("=== EAT Calculation Under Various Hit Rates ===\n\n");

    // Classic textbook example: 80% hit rate
    calculate_eat(0.80, tlb_latency, ram_latency);
    calculate_speedup(0.80, tlb_latency, ram_latency);
    printf("\n");

    // Modern CPU: 99% hit rate
    calculate_eat(0.99, tlb_latency, ram_latency);
    calculate_speedup(0.99, tlb_latency, ram_latency);
    printf("\n");

    // Sweep across hit rates
    printf("=== Hit Rate Sweep ===\n");
    double rates[] = { 0.0, 0.25, 0.50, 0.75,
                       0.90, 0.95, 0.99, 1.00 };
    for (int i = 0; i < 8; i++) {
        calculate_eat(rates[i], tlb_latency, ram_latency);
    }

    return 0;
}

Use code with caution.

💻 CODE DISSECTION: TRACING LATENCY WEIGHTS

Walking the EAT Arithmetic Trace

hit_rate * (tlb_ns + ram_ns)

The hit path weight. For 80% hit rate with TLB=20, RAM=100: 0.80 × (20 + 100) = 0.80 × 120 = 96 ns. This is what contributes when the TLB hits — one memory access.

(1.0 − hit_rate) * (tlb_ns + 2*ram_ns)

The miss path weight. For 20% miss rate: 0.20 × (20 + 200) = 0.20 × 220 = 44 ns. This contributes when the TLB misses — two memory accesses (page table + data).

eat = 96 + 44 = 140 ns

The final result. Average memory access time is 140 ns, dominated by the 96 ns hit contribution. The 44 ns miss contribution is smaller because misses are rare.

calculate_speedup

Compares EAT to the no-TLB baseline: 2 × 100 = 200 ns. At 80% hit rate, 200 / 140 = 1.43× speedup. At 99% hit rate, 200 / 121 = 1.65×.

The Takeaway

Even at 50% hit rate, EAT = 170 ns is better than the 200 ns no-TLB baseline. Above ~50% hit rate, the TLB always pays for itself. Modern CPUs exceed 95% — the TLB is essentially mandatory.

The Asymptote

At 100% hit rate: EAT = TLB + RAM = 120 ns. There is no way to go below this — the TLB lookup itself costs time. The 20 ns TLB overhead is the permanent tax paging pays, even in the best case.

🎯 INTERACTIVE WORKSHOP: THE LIVE EAT CHALLENGE

The Real-Time Latency Math Challenge

The Setup

Instructor writes the EAT equation on the board. Students are given TLB=10 ns and RAM=150 ns.

The Challenge

Instructor changes the hit rate live:

· 95% → what is EAT?

· 50% → what is EAT?

· 20% → what is EAT?

· 0% → what is EAT?

The Discovery

At 0% hit rate: 10 + 300 = 310 ns. Notice this is worse than the no-TLB baseline of 300 ns — because the TLB lookup itself adds 10 ns even when it always misses.

The Point: The TLB worsens performance when hit rate is 0% — but at realistic 95%+ hit rates, it delivers 1.6× speedups. This is why cache-friendly code (loops, sequential access, small working sets) matters enormously in real applications. Writing cache-unfriendly array loops can choke execution performance even on the fastest CPU.

Lecture 13 — Virtual Memory, Demand Paging & Page Replacement Primitives (Module 3 Finale)

We have made paging fast — but we have not yet made it unbounded. A process's virtual address space is not limited to physical RAM; it can be larger.
